## Notify Slot Honesty

The topology can represent Codex's top-level `notify` array as a hook slot, and
`readHarness()` still reads that slot when present. But there is not yet a real
notify command in this package. The old `planHarness()` claimed the canonical
plan fired `notify` while `applyConfig()` only wrote the MCP server table. That
was a mismatch between the settled carrier and the applied substrate.

I changed the canonical applied plan to carry only the AGRODAO MCP edge. This is
less flashy, but it is more correct: a hook becomes canonical only when there is
a real hook program to project into config. Until then, `notify` remains a
readable topology coordinate, not an invented applied behavior.

## AGRODAO Discovery Tools

The companion harness server now gives Codex one route through AGRODAO instead
of hardcoding package script knowledge:

- `agrodao_request` can read `/.well-known/agrodao/transports`;
- the same tool can fetch a discovered OpenAPI document;
- the same tool can read a package-bin transport mount;
- the same tool can invoke a package bin over stdin/stdout EAVT JSONL.

That is the current loop for using the running host as a substrate: discover the
host, read the OpenAPI projection, then run the script transport that still
belongs to the package's `package.json#bin`.

## Remaining Gap

callback bolted onto config. It needs a carrier-backed event shape that can
normalize into Mark/Utterance facts and then be transported to AGRODAO or to a
package bin. Until that exists, the harness should keep saying only what it can
actually apply.

## Consolidation Note

I took a consolidation pass rather than adding another harness feature. The
AGRODAO package-bin route now uses `@emsenn/jsnode/workspace` for the standard
`package.json#bin` projection instead of carrying a host-local parser. That
keeps Codex's AGRODAO affordance intact while shrinking the amount of special
case manifest logic around the harness.

The live path after restart is still:

- Codex connects to `http://127.0.0.1:18805/codex/hub/mcp`;
- the hub discovers AGRODAO transports;
- `/jsnode-bins` serves the `@emsenn/jsnode` package bins over stdin/stdout
  EAVT.

The difference is ownership: jsnode reads and projects package facts, web
transports package bins, and AGRODAO mounts the transport.

## Harness Surface Contraction

The first AGRODAO bridge for Codex had too many tools. It exposed separate MCP
names for transport discovery, OpenAPI fetches, package-bin discovery, and
package-bin invocation. That made the harness look more capable while actually
making it harder to reason about.

I collapsed those four tools into one `agrodao_request` tool. It sends a GET or
POST to a path on AGRODAO and returns status, content type, body, and parsed JSON
when applicable. That still lets Codex read `/.well-known/agrodao/transports`,
read `/jsnode-bins/openapi.json`, list `/jsnode-bins/`, and POST EAVT to
`/jsnode-bins/<bin>`, but it does not multiply the MCP surface.

Readback of the active Codex config still shows:

- `language-intelligence -> language-intelligence`
- `agrodao -> agrodao`
- `You<->MCP<->AGRODAO: wired`

The persistent Codex process is not being claimed as started here; the verified
state is the config edge plus the slimmed AGRODAO request bridge.

The Codex-side tool names were also collapsed. The hub now exposes
`codex_config`, `codex_process`, and `agrodao_request` instead of one MCP tool
per process/config operation.

## Harness Product Recalibration

I searched current Codex and agent-harness material instead of adding another
feature.

What matters for this package:

- Codex app-server is the right model for a rich local harness: initialize,
  start/resume/fork threads, start/steer turns, stream item events, handle
  command and file-change approvals, and support dynamic tools.
- Codex SDK is the programmatic wrapper for controlling local Codex agents from
  internal tools.
- `codex exec --json` is the lower-friction automation bridge for CI and scripts.
- Hooks are real, but they need a trusted lifecycle event contract; adding them
  before the event carrier exists would recreate the route/tool sprawl.
- The strongest harness research direction is observability-driven evolution:
  component observability, trajectory evidence, and decision records that can be
  checked against later outcomes.

So the Codex package should grow toward a small, evidence-rich control plane:
read/apply config, supervise or connect to app-server/exec streams, normalize
events into carriers, and let AGRODAO publish those carriers over its existing
transport index.

## Exec Events Onto Trace Carriers

I added a narrow Codex exec event projection instead of adding another command,
route, or MCP tool.

`src/session/events.mts` parses `codex exec --json` newline-delimited events and
projects them into `@emsenn/animating/trace` entries. The carrier keeps:

- the raw parsed event list;
- the trace entries;
- the utterances those entries descend to;
- the folded trace readings measured from the induced topology.

The exported shape is intentionally a boundary projection:

- `parseCodexExecJsonl`;
- `parseCodexExecTraceJsonl`;
- `codexExecTraceEntries`;
- `codexExecTrace`.

This gives the Codex package an evidence substrate for streamed exec runs
without making a new persistence model or expanding the AGRODAO route/tool
surface.

## Upstream Carrier Map

I read the upstream packages that should carry Codex state before this package
adds more logic.

Useful existing carriers:

- `@emsenn/animating/algebra`: `Task`, `Observation`, and the descent cycle for
  articulating work into predication cells and settled charges.
- `@emsenn/animating/session`: `Session` and charged `Finding`s for episodic
  working memory. This should back long-running Codex plan/task/decision memory;
  markdown journals are only a readable projection.
- `@emsenn/animating/trace`: trace entries -> utterances -> folded cell readings.
  This is the right home for Codex JSONL evidence.
- `@emsenn/animating/decision` and federation governance: auditable
  act/abstain/admission decisions with carried justification, useful for
  approvals, deploys, and destructive operations.
- `@emsenn/animating/fleet`: `WorkItem`, `WorkAssignment`, office recognition,
  eligibility, and dispatch readiness. This is the right shape for "what work is
  pending" and "which harness/agent can do it".
- `@emsenn/computing/computer`: observation provenance and run judgments. This
  should be the bridge from package `bin` scripts and EAVT IO into executable
  harness moves.
- `@emsenn/gaming`: arenas and strategies for the richer interactive move space
  once the simpler trace/session/work carriers are wired.

Next implementation bias: project Codex exec/app-server events into
`animating/session` findings and `animating/fleet` work reports before adding
new Codex-specific classes. If AGRODAO needs a UX, serve these existing carriers
through the existing transport index rather than creating another route family.

## Exec Events Onto Session And Fleet Carriers
