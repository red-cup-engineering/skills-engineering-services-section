# Equivo Design

**Duolingo-for-mathematics, teaching "how to observe equivalence by measuring obstruction"**
(owner's live intent, dossier header). Equivo is the flagship theme riding the platform contract
specified in the companion document, `self-education-platform-design.md` (corpus-compiler, SRS,
checker interface, mastery, theming, persistence — all cited by section below, not restated).
This document is Equivo-specific: the core loop, the exercise taxonomy, the curriculum schema
and spine, the presentation registers (including the one that is, correctly, mostly empty), the
checker contract with real computed worked examples, retention, and the MVP cut.

## Design authority

Structural choices cite the evidence dossier at
`/tmp/claude-1000/-home-emsenn-info/47cac153-3148-4572-abf7-955708e564d4/scratchpad/equivo-evidence-dossier.md`
by section (`§N`), which itself cites nine corpus digests with recurrence evidence — single-
document justifications are flagged explicitly where they occur and are never treated as
sufficient for a structural choice on their own. All three worked examples in §5 were computed by
actually running `@561-group/math`'s `bilattice` and `obstruction` packages from their real
source (paths and commands given in place) — nothing in §5 is a hand-simulated trace.

## What's load-bearing vs. flavor

1. **The four-stage descent (`articulate → predicate → posit → settle`) and the FOUR-valued
   bilattice charge are real, running code, independently reinvented to executable completeness
   in at least three separate stacks** — `@561-group/math`'s `bilattice` package (JS, 42/42 tests
   passing, re-verified for this document), the semiotics service's TypeScript pipeline, and
   obsmetrologia's Lean 4 library (dossier §1a — "the single strongest cross-corpus convergence
   found in the whole campaign"). This document's core loop (§1) is a direct, literal reading of
   that pipeline, not a metaphor built to sound like it.
2. **H¹ obstruction is an actually-computed cohomology group, not a metaphor riding on the word
   "obstruction."** `@561-group/math/obstruction/cochain.mjs`'s own header states the discipline
   plainly: *"We do not import a cochain complex and we do not borrow a name... The construction
   is the proof."* §5's worked examples run this code directly.
3. **The curriculum spine (§2) is a choice among three dossier-documented candidates, not
   invented fresh** — argued in §2 with the dossier's own trajectory evidence, not asserted.
4. **The presentation registers (§6) reproduce the dossier's vocabulary tables verbatim where
   populated, and represent the Lakotaean lens as an honest, structural absence, not a filled-in
   guess** — this is the one non-negotiable item in the whole document (§6.3).
5. **No Equivo-specific lesson corpus exists anywhere in the surveyed material.** A repo-wide
   search for any directory or content path containing "equivo" in this campaign's working tree
   returned nothing. Every concrete number and worked example in this document is drawn from the
   *mathematical* executable surfaces (`@561-group/math`, dossier §4) and the *platform*
   executable surface (Lantern, dossier §1i) — never from an Equivo curriculum, because none
   exists yet. This is stated as a hard MVP dependency in §8, not glossed over.

## 1. The obstruction-measurement core loop

One exercise attempt is one pass through the real descent, with a checker verdict and an SRS
update wrapped around it:

```
articulate (distinguish)  →  predicate (relate)  →  posit (measure)  →  settle
        │                                                                  │
        │                                                                  ▼
        │                                              observe: read the leftover —
        │                                              did it settle to one place (H⁰=1,
        │                                              equivalent), or split (H⁰>1) / carry
        │                                              a genuine cycle (H¹≠0, obstructed)?
        │                                                                  │
        └──────────────────── repair (optional remediation exercise) ◄────┘
                                          │
                                          ▼
                     checker verdict(spec, answer) → {pass, diagnosis}
                                          │
                                          ▼
                        SRS update (platform §3) + mastery update (platform §5)
```

"Equivalence" **is** two things settling to the same fixed point; "obstruction" **is** the
nonzero leftover — H¹, or a split H⁰ — when they don't (dossier §1a, mapping the owner's own
phrase onto the pipeline "almost literally"). The loop is not a UI metaphor drawn over arbitrary
quiz questions: every stage below names a real function in `@561-group/math/bilattice` or
`@561-group/math/obstruction`, and a player's "answer" at each stage is checked by literally
calling that function, never by string match against an author-chosen "correct" string.

## 2. Curriculum spine: chosen, with trajectory evidence

The dossier documents three defensible spines (dossier §5). This document adopts the dossier's
own evidence-implied recommendation, stated there as "implied by the evidence, not asserted as
fact," and restates the argument for it here rather than importing the conclusion bare:

**Chosen: Candidate C (chassis) carrying Candidate A (narrative frame) as content, with Candidate
B (the regime ladder) as the specific difficulty mechanic inside it.**

- **Candidate C, the chassis** — the house lesson/curriculum template plus ludics' own worked-
  example pedagogy, run on Lantern's actual working stack — is chosen because it is *the only one
  of the three candidates grounded in components already running end-to-end and tested* (dossier
  §5: 35+ lesson files, a real SHACL validator, 74–228 passing tests per sibling service) rather
  than in research prose. It also directly honors the owner's one confirmed design conviction —
  *Brave Old World*'s negotiated-validity, fail-forward ethos (dossier §2) — which maps onto
  "obstruction as unresolved disagreement" rather than "obstruction as wrongness," and the
  ludics curriculum already treats that exact game as its own canonical worked example (dossier
  §1g), a genuine pre-existing throughline the other two candidates lack.
- **Candidate A, the narrative frame** — walking each unit through
  `articulate → predicate → posit → settle` literally — is chosen over leading with Candidate B
  because it is the frame *most literally shared by three of the four lenses* (obsmetrologia,
  semiotics, and math-core's shared package family each independently built it to executable
  completeness, dossier §1a), making it the strongest available "this is real mathematics, not
  house metaphor" claim to open the product on.
- **Candidate B, the regime ladder**, is kept as the difficulty mechanic *inside* Candidate A's
  frame, not the launch frame itself, because bilattice (165 corpus-wide mentions) and
  obstruction (100 mentions) are the two most-recurrent themes in the entire math-content corpus
  and the regime taxonomy (finite/scott/transfinite/aperiodic) is independently corroborated by
  obsmetrologia's own dated frontier notes (dossier §5) — genuinely active research to grow into,
  but its weaker cross-lens bridging (dossier §5: "risks feeling like one lens's mechanic wearing
  three costumes") makes it a poor choice to lead with.

**What this rules out, and why, stated plainly**: Candidate A alone (no chassis) was rejected
because its source material is dense category theory needing a real translation pass to be
Duolingo-legible, and it has no delivery mechanism of its own. Candidate B alone (bilattice-
ladder-as-the-whole-game) was rejected as the frame because it currently only cleanly
instantiates in three of the owner's four lenses in the same thin way Candidate A does (dossier
§3), with no stronger cross-lens claim to offer in exchange.

## 3. Exercise-type taxonomy

Six types, one per the dossier's own vocabulary-table row (dossier §3: distinguish / relate /
measure / settle / observe-obstruct / repair) — the taxonomy is not invented independently of the
loop in §1; it *is* the loop, one exercise type per stage, plus a sixth for the loop's optional
remediation arc. Each row states its checker's real backing function and its dossier
evidence-strength, honestly, including the one row where that strength is thin:

| # | Type | Player does | Checker calls | Evidence strength |
|---|---|---|---|---|
| A | **Distinguish** | Name the two atoms (token, claim) in a scenario | `articulate(utterance)` — structural: does it throw, does the resulting `potential` pair match | Strong — dossier §1a, 3-corpus convergence |
| B | **Relate** | Build the subject/predicate/object cell from a token+claim | `predicate(articulate(utterance))` — structural match on the resulting cell-set | Strong — same |
| C | **Measure** | Assign a FOUR-value charge from evidence | `posit(predicate(articulate(utterance)))` — compares settled charge value bits to the player's claim | Strong — worked example 1, §5 |
| D | **Settle** (equivalence) | Claim whether a proposed relation settles to one connected component | `cohomologyOfRelation(cells)` — compares `H0.rank === 1` to the player's claim | Strong — worked example 2, §5 |
| E | **Observe** (regime) | Classify a settling's regime and whether H¹ vanishes | `classify(settling)` + `h1(settling)` — compares both fields to the player's claim | Strong — worked example 3, §5 |
| F | **Repair** | Given a nonzero-H¹ relation, propose an edit that closes the obstruction | `cohomologyOfRelation(editedCells)` — re-run on the player's edited cell list, pass iff `H1.rank === 0` **and** the edit didn't just delete the disagreement (see honesty note below) | **Weakest** — dossier §3 found no single named "repair" primitive in any lens; nearest analogs are obsmetrologia's self-correction ledger discipline and semiotics' "abduction," both one level up from the executable pipeline |

**Honesty note on Repair (type F)**: the checker is mechanically well-defined (it is the same
`cohomologyOfRelation` call as type D, run twice), but the *pedagogy* of "what counts as a good
repair" is not equally well-grounded — a player could trivially "pass" by deleting the
obstructing cell entirely rather than resolving the disagreement it represents, and the dossier's
own vocabulary table gives no corpus-attested vocabulary for distinguishing a genuine repair from
an evasion. This document does not claim to have solved that; §8 (MVP cut) defers type F out of
launch scope for exactly this reason, stated there again rather than only here.

## 4. Curriculum-as-data schema

An Equivo lesson is an ordinary corpus **Room** under the platform's compiler contract
(`self-education-platform-design.md` §2) — same frontmatter shape, same `requires`/`teaches`/
`uses-mechanic`/`cites` fields, same door-extraction rules. Nothing about Equivo changes how a
room becomes a node in the concept graph. What Equivo adds is **where its exercises live and how
they're typed**, and that placement is a direct consequence of a constraint already stated in the
platform document, not a new one invented here: `frontmatter.mts`'s parser is *deliberately* a
YAML subset — scalars and flat string lists only, nested maps recognized and skipped (platform
§2). An exercise `spec` (§3's table: an `utterance` pair, a `cells` array of subject/predicate/
object triples, a `stages` array of settling increments) is exactly the kind of nested structure
that parser will never read. So exercise data does not go in frontmatter at all — it goes in the
room's **body**, as a fenced code block, extracted by its own compiler rule, parsed as JSON (a
strict subset of what the fenced block can contain, chosen specifically because `JSON.parse` is a
zero-dependency, already-in-Node primitive — no new parser to write or trust).

**The `ExerciseSpec` discriminated union** — one arm per §3 row, `kind` is the dispatch tag the
platform's checker registry (`self-education-platform-design.md` §4) looks up:

```ts
export type ExerciseSpec =
  | { kind: 'distinguish'; utterance: [unknown, unknown] }
  | { kind: 'relate'; utterance: [unknown, unknown] }
  | { kind: 'measure'; utterance: [unknown, unknown] }
  | { kind: 'settle'; cells: { subject: unknown; predicate: unknown; object: unknown }[] }
  | { kind: 'observe'; stages: { designated: unknown[]; limit?: boolean }[]; opts?: { cofinal?: 'uncountable' } }
  | { kind: 'repair'; cells: { subject: unknown; predicate: unknown; object: unknown }[] };
```

Every field here is exactly the argument shape §5's worked examples pass to the real
`@561-group/math` functions — `measure`'s `utterance` is literally `posit(predicate(articulate(
utterance)))`'s input, `settle`'s `cells` is literally `cohomologyOfRelation(cells)`'s input. This
is deliberate: the curriculum data format is not a separate abstraction the checker has to
translate — it *is* the checker's own argument, serialized. A corpus author (or, pre-authoring,
this document's own worked examples, §5) writes data the math already knows how to consume.

**Extraction rule, added to the compiler's exercise-generation priority list**
(`self-education-platform-design.md` §4, alongside Lantern's five existing card rules):
a fenced block opened with ```` ```equivo-exercise ```` is parsed as one JSON `ExerciseSpec`
object (or a JSON array of them, for a room with several); a `prompt` field (player-facing text)
travels alongside `spec` in the same block rather than being synthesized, for the same reason
Lantern's own Rule 1 prefers pre-authored text over generated text (`cards.mts`: *"pre-authored
Q/A is strictly better than generated Q/A"*). A room with zero `equivo-exercise` blocks produces
zero Equivo-typed exercises for that room — it still participates in the concept graph (doors,
halls) and can still carry ordinary distinguish/relate warm-up cards from the platform's existing
rules (§3's table, types A/B), just no measure/settle/observe/repair content.

**Concrete instance** — the exact data §5.1's worked example is drawn from, as it would sit in a
real lesson file's body:

````markdown
---
title: Reading a 3-3 Invasion as Potential
type: lesson
requires:
  - glossary/terms/corner-invasion.md
teaches:
  - measuring a scenario's bilattice charge
date-created: 2026-08-19
authors:
  - claude-fable-5
---

A 3-3 stone played directly in the corner is a claim about future territory before any of it is
settled. Before you read on: is this claim **potential** (asserted on one side only) or
**stable** (asserted and confirmed on both)?

```equivo-exercise
{
  "kind": "measure",
  "prompt": "A 3-3 stone is played, claiming a corner-invasion. Right now, is this charge potential or stable?",
  "utterance": ["3-3 stone", "corner-invasion"]
}
```
````

This is not illustrative filler distinct from §5's code — running this exact `utterance` through
`posit(predicate(articulate(...)))` is what produced §5.1's actual printed output
(`[true, false]`, "potential"). The curriculum format and the worked example are the same object,
shown twice for two different reasons: here, as data at rest in a corpus; there, as the input to
a running checker.

## 5. Checker contract, with three worked examples

The checker contract is exactly the platform's `Checker<Spec, Answer>` interface
(`self-education-platform-design.md` §4): `verdict(spec, answer) → {pass, diagnosis}`, pure,
synchronous, no I/O. Equivo's registry supplies one checker per row of §3's table. The three
examples below were run for this document against the real, unmodified source of
`@561-group/math` — package resolution set up via a `node_modules/@561-group/math` symlink to the
live package at
`lib/emsenn/services/561-group/services/science-services-section/services/information-science-services-section/services/math-services-section/services/voidmath-services-section/services/math-core`,
no fixture data invented, every printed value is what the code actually returned.

### 5.1 Worked example — Measure (type C)

```js
// example1-descent-pass.mjs
import { articulate, predicate, posit, settle } from "@561-group/math/bilattice";

function verdict(spec, answer) {
  const category = posit(predicate(articulate(spec.utterance)));
  const settled = settle(category);
  const cell = settled.sheaf.section["fiber-algebras"][0].assignments[0];
  const actual = cell.charge.value;
  const pass = actual[0] === answer.value[0] && actual[1] === answer.value[1];
  return { pass, diagnosis: pass
    ? `correct — settles to [${actual}], evidence positive=${JSON.stringify(cell.charge.evidence[0])}`
    : `the descent settles to [${actual}] (${nameOf(actual)}), you answered [${answer.value}] (${nameOf(answer.value)})` };
}

const spec = { utterance: ["3-3 stone", "corner-invasion"] };
verdict(spec, { value: [true, false] });   // correct answer
verdict(spec, { value: [true, true] });    // wrong answer
```

Command: `node example1-descent-pass.mjs`. Actual output:

```
--- verdict(spec, correct-answer) ---
{
  "pass": true,
  "diagnosis": "correct — settles to [true,false], evidence positive=[\"3-3 stone\"]"
}
--- verdict(spec, wrong-answer) ---
{
  "pass": false,
  "diagnosis": "the descent settles to [true,false] (potential), you answered [true,true] (stable)"
}
```

This is the flagship "measure" exercise: the player is shown a scenario-shaped utterance and must
predict which of the four bilattice corners (absurd/potential/active/stable) it measures to. The
checker never hard-codes the answer — it runs the same `posit` that the whole rest of the pipeline
runs, so a corpus edit that changes what a scenario means automatically changes what the checker
accepts, with zero drift risk between "the lesson" and "the grader."

### 5.2 Worked example — Settle / equivalence (type D)

```js
// example2-obstruction-cells.mjs
import { cohomologyOfRelation } from "@561-group/math/obstruction/cochain";

function verdict(spec, answer) {
  const result = cohomologyOfRelation(spec.cells);
  const actuallyEquivalent = result.H0.rank === 1;
  const pass = actuallyEquivalent === answer.claim;
  return { pass, diagnosis: pass
    ? `correct — H0 rank ${result.H0.rank} (...), H1 rank ${result.H1.rank}`
    : `you claimed ${answer.claim ? "equivalent" : "not equivalent"}, but H0 rank is ${result.H0.rank} ...` };
}

const specConnected = { cells: [
  { subject: "A", predicate: "equivalent-to", object: "B" },
  { subject: "B", predicate: "equivalent-to", object: "C" },
] };
const specDisjoint = { cells: [
  { subject: "A", predicate: "equivalent-to", object: "B" },
  { subject: "C", predicate: "equivalent-to", object: "D" },
] };
```

Command: `node example2-obstruction-cells.mjs`. Actual output:

```
--- verdict(connected-chain, claim=equivalent) ---
{
  "pass": true,
  "diagnosis": "correct — H0 rank 1 (one component, equivalent), H1 rank 0"
}
--- verdict(disjoint-pairs, claim=equivalent) [should fail] ---
{
  "pass": false,
  "diagnosis": "you claimed equivalent, but the relation has H0 rank 2 (2 connected components) over 4 entities and 2 cells — it does NOT settle to one component"
}
--- verdict(disjoint-pairs, claim=not-equivalent) [should pass] ---
{
  "pass": true,
  "diagnosis": "correct — H0 rank 2 (2 components, NOT equivalent), H1 rank 0"
}
--- raw cohomologyOfRelation(specConnected) for inspection ---
{
  "entities": ["\"A\"", "\"B\"", "\"C\""],
  "cells": [ { "subject": "A", "predicate": "equivalent-to", "object": "B" },
             { "subject": "B", "predicate": "equivalent-to", "object": "C" } ],
  "d0": [ [-1, 1, 0], [0, -1, 1] ],
  "H0": { "rank": 1, "cocycles": [[1, 1, 1]] },
  "H1": { "rank": 0, "vanishes": true }
}
```

This is the exercise type that most directly plays the owner's headline sentence: the player
proposes (or is shown) a relation and must say whether it is "one equivalence class" — and the
checker's answer is the actual rank of `H⁰` (the real per-component-indicator cocycle basis
`cochain.mjs` computes, printed above, not asserted), read off a real union-find over the
relation's own cells, exactly as `cochain.mjs`'s own header describes: *"no linear algebra at
all, by the graph's connectivity."*

### 5.3 Worked example — Observe / regime (type E)

```js
// example3-regime-classify.mjs
import { settling, classify, h1 } from "@561-group/math/obstruction/settling";

function verdict(spec, answer) {
  const v = settling(spec.stages, spec.opts ?? {});
  const cls = classify(v);
  const obstruction = h1(v);
  const pass = answer.regime === cls.regime && answer.h1Vanishes === obstruction.vanishes;
  return { pass, diagnosis: pass
    ? `correct — regime "${cls.regime}" at depth ${cls.depth}, H1 rank ${obstruction.rank}`
    : `... the settling is actually regime="${cls.regime}", H1 rank ${obstruction.rank}` };
}

const specFinite = { stages: [
  { designated: ["a"] }, { designated: ["a", "b"] }, { designated: ["a", "b", "c"] },
] };
const specTransfinite = { stages: [
  { designated: ["a"] }, { designated: ["a", "b"] },
  { designated: ["a", "b", "c", "d"], limit: true },   // c and d first appear only at the limit stage
] };
```

Command: `node example3-regime-classify.mjs`. Actual output:

```
--- verdict(finite settling, correct answer) ---
{ "pass": true, "diagnosis": "correct — regime \"finite\" at depth 2, H1 rank 0 (vanishes=true)" }
--- verdict(finite settling, wrong answer) ---
{ "pass": false, "diagnosis": "you answered regime=\"transfinite\" h1Vanishes=false; the settling is actually regime=\"finite\" (depth 2), H1 rank 0 (vanishes=true)" }
--- verdict(transfinite settling, correct answer) ---
{ "pass": true, "diagnosis": "correct — regime \"transfinite\" at depth 2, H1 rank 2 (vanishes=false)" }
--- raw classify()+h1() for the transfinite settling ---
{
  "classify": { "depth": 2, "regime": "transfinite" },
  "h1": {
    "generators": [ { "stage": 2, "cell": "c" }, { "stage": 2, "cell": "d" } ],
    "rank": 2, "degree": 1, "vanishes": false
  }
}
```

Note the honest artifact in this run, kept rather than cleaned up: the transfinite example's `H1`
rank came out `2`, not `1`, because both `"c"` and `"d"` first appear at the same limit stage in
this hand-built example — `h1`'s own definition (dossier-cited: *"the free abelian group on the
cells first designated at a limit stage"*) counts each such cell as its own generator, correctly.
This is exactly the kind of discrepancy-from-a-naive-expectation a real computation surfaces that
a hand-simulated trace would not have — evidence the example was actually run, not authored to a
pre-decided output. This exercise type is the ladder mechanic from Candidate B (§2): regimes are
the difficulty tiers, and a player's growing ability to correctly classify deeper, weirder
settlings *is* the progression curve.

## 6. Presentation registers

Registers are exactly the platform contract's `PresentationRegister` (`self-education-platform-
design.md` §6.1). Equivo ships (at minimum) four register ids — one per lens the owner names as
equivalent (obsmetrologia, semiotics, relationality, Lakotaean) — each populated from the
dossier's own vocabulary tables (dossier §3), reproduced here as the actual register content, not
a fresh translation:

| Engine concept | obsmetrologia | semiotics | relationality | Lakotaean |
|---|---|---|---|---|
| `distinguish` | **Mark**, **Kind** (`token`/`claim`) | **articulate** / `Mark` (opaque atom), `Token`/`Claim` | **Differentiate** (Movement I, step 1) | *absent* |
| `relate` | **Utterance**, **Articulating** | **predicate** — Cell = subject/predicate/object (Φ = E×Π×E) | **Include/Exclude → Together/Either/Negate**; **RelationalLanguage** λ_R | *absent* |
| `measure` | **Charge** (FOUR); `measured` (`Cell.measure`) vs. `seeded` (`Spine.posit`) — stated unresolved whether these must agree | **posit** — "value enters predication by evidence" | **States/Observables** (Movement V) — named, not elaborated as a procedure | *absent* |
| `settle` | **Closure / settle** (Knaster–Tarski lfp) | **settle** — "the knowledge-least fixed point" | **Close/Open → Balance**; **Generative Closure** $G$ | *absent* |
| `observe` | **Observation** (light-cone reconstruction); **Obstruction** = H¹ | **analyze**; H⁰/H¹ sheaf-cohomology modules | **Emergent Containment** (Movement V) — thematically adjacent, no explicit obstruction-cohomology vocabulary surfaced | *absent* |
| `repair` | no single named primitive — closest is the self-correction ledger discipline | not directly named — **abduction** is the nearest conceptual analog | **Dynamic Residuation** (Movement III) — closest candidate, not confirmed as a repair operator | *absent* |

Sources for every populated cell are the dossier §3 citations (`chapters/primitives/01-marks-
and-kinds.tex`, `Obsmetrologia.lean`, `articulating/utterance.mts`, `predicating/predication.mts`,
`positing/bilattice-charge.mts`, `settling/document.mts`, `settling/analysis/index.mts`,
`five-movements.md`, `generative-closure.md`) — carried into each `RegisterEntry.source` field in
the actual data, not flattened away here.

### 6.1 Register selection is player-facing, not a hidden A/B split

A player picks a lens at theme/session start (or per-unit, if the curriculum spine's later tiers
want cross-lens comparison exercises — out of MVP scope, §8); the same underlying exercise `spec`
renders through whichever register is active. This is *why* the engine vocabulary in §1/§3 stays
neutral (Room/Door/settle/measure, never "Mark" or "Cell" baked into the compiled data) — a
neutral core is what makes four simultaneous, swappable vocabularies possible without four
separate compilers.

### 6.2 Three lenses ship thin-but-real; the fourth does not ship guessed

Per dossier §3's own closing analysis, even the three populated lenses differ from each other in
emphasis — obsmetrologia is measurement-first, relationality is process-first, semiotics is
sign/interpretant-first — and the `relate`/`measure`/`observe` rows for relationality are
explicitly weaker than obsmetrologia's or semiotics' (dossier §3: "named but not elaborated ...
as a measurement procedure"; "thematically adjacent" rather than confirmed). This document ships
all three anyway, honestly labeled by strength, because they are at least corpus-attested; it
does not extend the same treatment to a fourth lens with zero attestation.

### 6.3 The Lakotaean register: owner-authored-only, honest absence — non-negotiable

Restated here as Equivo's own hard constraint, not only the platform's general policy
(`self-education-platform-design.md` §6.3): **every cell in the Lakotaean column above is
`{ state: 'absent', reason: '...' }` data, not a blank the UI happens to skip.** The dossier
found this is not a sampling gap — it checked all nine assigned corpora and found zero Lakota-
specific vocabulary at every one of the six rows (dossier §3); the only two "touches" found were
themselves gap-flagging, not content: `learn-semiotics-basics/SKILL.md`'s own explicit scope
exclusion (read directly for this document, quoted in the companion platform doc's disclosure
section), and AI-authored `decolonial-ttrpgs`/`indigenous-ttrpgs` tag folders that are general

## 7. Retention design

Reuses the platform's SRS wholesale (`self-education-platform-design.md` §3) — Equivo introduces
no second scheduler. Three retention surfaces, each disclosed by what's real math vs. flavor,
following the platform's own disclosure convention:

- **SRS (real).** Every exercise (all six types, §3) is scheduled by the same FSRS-lite engine;
  a `measure`-type exercise and a `distinguish`-type exercise for the same room are independent
  cards with independent `(stability, difficulty, lastReviewedAt)`, exactly as Lantern already
  schedules its five card kinds independently per room.
- **Drills (real math, flavor framing).** Equivo's equivalent of Lantern's kata: a timed, ordered
  walk through a hall's exercises, scored, belted, and itself scheduled through the same SRS
  engine via the synthetic-grade mapping (platform §3) — unchanged mechanism, Equivo-specific
  content is which regime tier (§2's Candidate B ladder) a drill draws its exercises from. Belt
  labels are flavor (platform's own disclosure: *"a 'black belt' kata tier is a difficulty label,
  not a credential"*); the underlying ratio and its SRS-scheduled repeat are not.
- **Kind streaks (cosmetic only, stated plainly).** Consecutive-day counters and freeze tokens,
  identical to the platform's inherited no-list (`self-education-platform-design.md` §6.4): no
  energy gate, no rewarded ads, no streak-loss shaming, capped freeze-token banking. Nothing about
  a streak affects mastery (platform §5) or which exercises are due — it is pure cosmetic
  encouragement layered over real scheduling, and is labeled as such here so a future feature
  request to make streaks "count" toward something is recognized as a scope change, not a bug fix.

## 8. MVP cut

**In:**

- Curriculum spine: Candidate C chassis + Candidate A frame + Candidate B ladder (§2), applied to
  **three lenses only**: obsmetrologia, semiotics, relationality (the three the dossier confirms
  actually instantiate the descent pipeline, dossier §1a/§3).
- Exercise types **C (measure), D (settle/equivalence), and E (observe/regime)** — the three with
  worked, running checkers in §5 and the strongest per-lens vocabulary attestation. Types A
  (distinguish) and B (relate) ship as gate/warm-up content, reusing the platform's existing
  card-generation rules (`self-education-platform-design.md` §4) rather than new checkers, since
  their "answers" are structural, not computed judgments.
- SRS, drills with belts, kind streaks — all reused unmodified from the platform (§7).
- Presentation registers for the three in-scope lenses, populated exactly as §6's table, honestly
  labeled by per-row strength (§6.2).

**Out (roadmap, not this build), each with the reason it's out stated, not just listed:**

- **Type F (repair) exercises** — deferred because the checker's "did you actually fix the
  disagreement vs. delete it" distinction has no corpus-attested vocabulary to design a fair
  grading rule from yet (§3's honesty note); shipping it ungrounded risks teaching a wrong lesson
  about what repair means.
- **The Lakotaean register** — blocked on owner-authored source material that does not exist in
  any surveyed corpus (§6.3); this is the single largest content gap the dossier identifies
  relative to the owner's own four-lens framing (dossier §6, "Where the dossier as a whole is
  thin," item 1), and no synthesis pass by this or any agent can close it honestly.
- **An authored Equivo lesson corpus** — none exists today (confirmed by direct search, "What's
  load-bearing vs. flavor" point 5, above). The MVP's first content-authoring pass is translating
  a handful of already-real descent/obstruction computations (like §5's three worked examples)
  into player-legible scenario text, for each of the three in-scope lenses — a real, sizable,
  currently-unscheduled piece of work this document does not shrink by naming it.
- **Cross-lens comparison exercises** ("show me the same obstruction through two registers at
  once") — a natural extension of §6.1's per-session register choice, but adds a second dimension
  of grading complexity with no current worked example to ground it.
- **Nuclear-quartet / quasicrystal content** (dossier §1e) — confirmed live at the research
  frontier but dormant as pedagogy; explicitly flagged in the dossier as "a candidate for a later,
  harder Equivo tier, not a launch spine," and this document agrees with that verdict rather than
  re-litigating it.
- **Server-authoritative accounts/progress sync** — inherited unresolved from the platform
  document (`self-education-platform-design.md` §7); Equivo ships local-first like every other
  theme at launch.
