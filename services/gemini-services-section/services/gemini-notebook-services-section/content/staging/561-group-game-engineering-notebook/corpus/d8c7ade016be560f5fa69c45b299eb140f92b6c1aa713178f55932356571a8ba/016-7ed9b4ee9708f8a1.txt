## 1. Introduction and goals

onestone (storefront name **TileSlots**) is a browser match-3 whose stated differentiator, per
`DESIGN.md`, is "the one thing no incumbent has touched in a decade: the grid itself." Chapter 1 is
an onboarding-free square 8×8 board; chapter 2 moves to hex; chapter 3 to rhombille — the same one
match/cascade engine (`engine.mts`) runs every tiling unmodified, because every tessellation
compiles down to one shared `BoardGeometry` (`types.mts`, `tiling-core.mts`). This is the fleet's
**second-generation** service: its `DESIGN.md` explicitly inherits flickering-delve-service's
doctrine, and this document confirms by direct read that the inheritance is real, not aspirational
(§9 ADR-1).

## 2. Constraints

- **Determinism.** `seed.mts` (86 lines, unread in full for this document but confirmed structurally
  identical in role to flickering-delve's own — FNV-1a `hashSeed` + mulberry32 `makeRng`) is the only
  randomness source `engine.mts` and `levels.mts` consume. A repo-wide grep of `src/*.mts` for
  `Date.now\(\)` turns up exactly one call site: `payments.mts`'s default `date: () => new
  Date().toISOString().slice(0, 10)` constructor parameter — an injected default at the impure
  boundary, always overridable, never called from inside a pure function. `Math.random()` appears
  nowhere in `src/`.
- **Zero runtime dependencies beyond the pinned `@561-group/*` house exception.** `package.json`
  had no `dependencies` key at all at original writing; this update adds exactly one,
  `@561-group/cartridge@^0.1.0` (installed from the local Verdaccio registry — a project-level
  `.npmrc` scoping `@561-group:registry` to `http://127.0.0.1:4873/`, matching the pattern already
  established by `crucible-service`/`play.561.group`, was added alongside it), per the house
  standard's own §2 exception for vendored `@561-group/*` packages. `sideEffects: false` and Node
  builtins otherwise.
- **One stateful scene.** `scene.mts` (418 lines) is the sole mutable-state module — its own header
  states this explicitly and correctly: "Every other module in this repo is a pure function of its
  arguments... This module is where that purity earns its keep." `engine.mts` (1,010 lines,
  the largest module in the service) is, by direct inspection, entirely pure: every exported
  function takes its geometry/state as a parameter and returns a fresh object; the module's own
  header states the discipline ("Every exported function is pure: inputs are never mutated") and
  the claim holds — no `let`-mutation of a passed-in `BoardState`/`BoardGeometry` was found in any
  code path read for this document.
- **Vendor-not-import, confirmed by diff.** `ledger.mts` and `payments.mts` were directly diffed
  against flickering-delve-service's own during this document's research: `ledger.mts` differs only
  in doc-comment wording (plus one commodity-list edit, "HIVE/HBD" → "HIVE"); `payments.mts` differs
  in type re-exports (`Sku`/`Order` now imported from the shared `types.mts` rather than declared
  locally) but the `PaymentProvider` boundary, all three adapters, and the settle/idempotency logic
  are the same shape. This is the house pattern working exactly as `DESIGN.md` claims — "near-verbatim
  ports."

## 4. Solution strategy

"The board is a graph, not a grid." One compiler (`tiling-core.mts::compileGeometry`) turns any
tiling's unit-scale polygon output into a shared, tiling-agnostic `BoardGeometry`: shared-edge
adjacency (discovered by canonical quantized edge keys, never proximity or shared vertices — a
genuine engineering choice, not an obvious one, since a corner-touch at a square-grid diagonal must
*not* count as adjacency), a baked `fallTo`/`fallFrom` +y gravity field (not a live physics sim,
because settle order must be exactly reproducible), and precomputed straight-line `rails`
generalizing "row/column" to any tiling via a 30°-tolerance "opposite-ish neighbor" walk. `engine.mts`
never branches on `TilingKind` — confirmed by grep: the string literals `'square'`/`'hex'`/`'rhombille'`
appear nowhere in `engine.mts`, only in `tiling.mts`'s one dispatch switch and the three
`tiling-*.mts` cell producers.

## 6. Runtime view

**Scenario A — a swap that fires a compound special pair, traced through the settle loop.**
`POST /input {token, input:{kind:'swap', a, b}}` (`server.mts:319-334`) resolves the account via
the per-account FIFO (`makeFifo()`, `server.mts:184-202` — ensures two concurrent requests for the
same account apply in arrival order to the synchronous scene) and calls `scene.input(account,
input)`. `dispatchInput` (`scene.mts:275-288`) routes to `handleSwap` (`scene.mts:210-218`), which
calls `engine.mts::applyMove` (`engine.mts:958-980`): the two tiles swap, `findMatches` runs on the
swapped state, and — if at least one side carries a special — `swapFire` is built with the
**post-swap** cell positions (`aCell`/`bCell` name where each original tile *landed*, not where it
started, per the module's own inline comment at `engine.mts:971-976`). `settleLoop`
(`engine.mts:894-941`) then runs to a fixed point: each iteration calls `runStep`, which mints
specials at match origins, drains chained special fires via a BFS-style queue
(`drainSpecials`, `engine.mts:789-806`), resolves the swap's own compound pair through
`fireSwapSpecials` (`engine.mts:562-612` — the four named pairs: striped+striped, striped+nova,
prism+prism, prism+striped; every other combination falls through to independent solo fire, per the
module's own comment "not in DESIGN.md's compound table... never silently drops a special"),
resolves blocker hits (`resolveHits`, direct-hit and adjacency-effect passes), falls tiles to a
fixed point (`settleFall`), and refills spawn mouths from the same seeded draw stream refill uses
(`refill` → `drawColor`, rejection-sampled, with an exhaustive deterministic fallback if every
random attempt in `paletteSize * 6` tries lands on an unsafe color). `scene.mts::applySettleToRun`
folds the resulting `CascadeStep[]` into goal progress via `levels.mts::goalProgressFrom`, and
`finishOrContinue` checks whether every goal is now met (or moves are exhausted) before deciding
whether the level just ended.

**Scenario B — level generation as a seeded search against the pebble-game oracle, not a formula.**
`levels.mts::buildChapter` (`levels.mts:299-317`) walks 20 levels per chapter, feeding each level's
*achieved* mean coordination forward as the next level's floor (never regressing the ramp). For
each level, `buildBlockers` (`levels.mts:174-209`) sweeps blocker counts upward, at each count
sampling several random placements via the level's own in-module mulberry32 RNG, calling
`validate.mts::blockerEdges` then `pebbleIndependent` on the resulting constraint graph, and keeping
whichever independent layout minimizes the gap to the target mean coordination — never the first
layout that merely clears a threshold. `buildLevel` (`levels.mts:256-295`) then runs the whole
candidate `LevelSpec` back through `validate.mts::validateLevel` (which independently re-derives the
geometry, spawns the board, applies blockers, and checks palette bound / legal-move existence /
pebble-independence / coordination-within-0.05 / goal achievability), retrying with salted reseeds
up to 12 times if validation fails. This is a genuinely constructive search against a real
independence oracle, not a lookup table or a hand-tuned curve — the 60-level `LEVELS` export is a
module-load-time computation, and `levels.test.mts`/`validate.test.mts` assert all 60 pass
`validateLevel` as the final word.

**Scenario C — a `/pay` purchase resolving synchronously through the mock provider.** `POST /pay
{token, skuId}` (`server.mts:336-359`) calls `payments.intent()` then immediately calls
`payments.settle(intentResult.orderId)` in the same request — for the mock provider this clears
instantly (`payments.mts`, same shape as flickering-delve's `mockProvider`), and the route calls
`scene.grantSku(grant.order.account, grant.sku)` before responding. `scene.mts::grantSku`
(`scene.mts:383-387`) calls `economy.mts::grantSku` (a pure switch over the SKU's bounded `grant`
union — `prisms`/`booster`/`lives`/`pass`, never anything else, enforced by TypeScript's exhaustiveness
check at `economy.mts:220-223`) and emits the updated frame to any subscribed SSE stream.

## 8. Crosscutting concepts

- **Replay verification: RESOLVED 2026-08-19 (this update).** `applyMove` and `applyBooster` were
  already pure and deterministic given `(geometry, state, move)` — the precondition for replay to
  work — and `cartridge-and-energy-bank-spec.md` §1.2's own assessment ("`defaultReplay`... is
  exactly the missing piece, buildable purely from the already-pure `applyMove`") is now acted on:
  `src/cartridge.mts::replay` delegates to `@561-group/cartridge/replay`'s own `defaultReplay`, and
  `src/cartridge.manifest.mts::verify` is the standalone `(seed, configId, intents) => {valid,
  finalState, events, stateHash}` function a settlement backend or the storefront's audit page
  would call — §9's new ADR and §11 item 3 have the full account. `cartridge.test.mts` asserts the
  determinism property directly: same seed + same intent log, replayed twice, yields byte-identical
  `finalState` and `stateHash`.
- **Ledger invariants.** `AuditLedger.record` refuses unbalanced entries (identical mechanism to
  flickering-delve, §2). `payments.mts::Payments.settle` posts only to `assets:cash:{provider}` /
  `income:premium` — same income-only posture as the sibling service; no `liabilities:*`/
  `expenses:payout:*` account family exists here either, so the Energy Bank's
  `verifyPayoutInvariant` does not yet apply (there is no payout direction to violate it).
- **Ethics as executable tests — the fleet's strongest instance.** `types.mts`'s own doc comment on
  `Sku['grant']` states the constraint in the code itself: "never a flat resource grant... never a
  level-solvability shortcut (solvability is a validated mathematical property of the board;
  selling around it would falsify the game's own math claim)." This is not merely policy prose: it
  is enforced structurally by `validate.mts::validateLevel` gating every one of the 60 shipped
  levels at generation time (Scenario B), and the shop (`economy.mts::SKUS`) has no grant kind that
  could touch board solvability at all — the TypeScript union itself makes an unbounded grant a
  compile error, not merely a review-time judgment call. `economy.test.mts` and `levels.test.mts`
  both assert pieces of this (bounded rewards; all 60 levels validate) directly.
- **Accessibility.** `TILESLOTS-DESIGN.md` §1.4 specifies a `prefers-reduced-motion` fallback for
  screen shake (a single flash-white frame instead) and a color-blind-considerate palette
  requirement (distinct lightness + glyph per color). This document confirms these are
  **specified, not yet implemented**: `client.mts` at time of reading still renders via inline SVG +
  CSS transitions (the pattern `TILESLOTS-DESIGN.md` itself names as the confirmed gap to replace
  with layered Canvas 2D) — the accessibility requirements ride on top of a renderer rewrite that
  has not landed yet, a real, named, scoped piece of debt (§11).

## 9. Decisions (ADRs), recovered from the code

- **ADR-1: doctrine inheritance from flickering-delve-service is real, confirmed by diff, not
  merely claimed in prose.** Evidence: §2's direct `ledger.mts`/`payments.mts` diff, run for this
  document.
- **ADR-2: rejection-sampled fill, not a proper graph coloring — corrected in the code's own doc
  comments after an earlier overclaim.** `engine.mts`'s header states this exactly: "That is NOT a
  proper coloring of the adjacency graph in the graph-homomorphism sense... `chi(K4)=4` and the
  5-color headroom are real, useful facts about the palette size; 'graph homomorphism into
  K_palette' is not an accurate description of what `wouldCreateMatch` actually enforces." This is a
  recovered ADR with its own correction history stated plainly in the source — exactly the honesty
  pattern the house theory-binding section (§13) requires, already present here before this
  document existed.
- **ADR-3: cascade termination is graph-theoretic acyclicity, not Knaster-Tarski — a second,
  parallel self-correction.** `engine.mts`'s header: "refill injects brand-new RNG-drawn tiles every
  round, so there is no such lattice [for Knaster-Tarski to apply to]... The actual reason the happy
  path terminates is purely graph-theoretic: `tiling-core.mts`'s `fallTo` requires strictly-greater-y
  alignment... so the fall graph is acyclic and every tile can fall only a bounded number of times."
  `README.md` (not yet updated at time of this document's writing) still states the Knaster-Tarski
  framing without this correction — a real, small, documented-elsewhere-but-not-here inconsistency
  worth flagging (§11).
- **ADR-4: `server.mts` takes every collaborator as an injected structural interface rather than
  importing concrete siblings at module scope.** The module's own header names the reason directly:
  onestone's sibling modules "are being built by other agents in parallel and may not exist yet."
  Evidence the choice is load-bearing, not decorative: `SceneLike`/`PaymentsLike`/`LedgerLike` are
  declared locally in `server.mts` rather than imported as values from `scene.mts`/`payments.mts`,
  and the concrete wiring only happens inside `main()`, gated by `isMain()` so it never runs on
  import — `server.test.mts` can and does exercise the whole route surface against mocks with none
  of the concrete sibling modules present.
- **ADR-5: `accounts.mts` was ported but never wired in — decided (2026-08-19) to delete it, not
  wire it in.** `scene.mts::slugAccount` (`scene.mts:128-131`) plus `SceneImpl`'s own inline
  `login()`/session `Map` already provide the identity layer live, tested (`scene.test.mts`), and
  wired through `server.mts`'s route surface — `accounts.mts::Accounts` was a second,
  independently-maintained implementation of the same slug-and-bearer-token pattern that nothing
  ever called (confirmed: the only reference anywhere in `src/` was a comment in `client.mts`
  naming its doc, never an import). The evidence favored deletion over wiring-in on three counts:
  (1) wiring it in would mean *replacing* `scene.mts`'s own already-correct, already-tested
  identity code with a second implementation for no behavioral gain — a straight regression risk
  for zero benefit; (2) `accounts.mts`'s `tokenActorId` prefixes ids with `tess-`, while
  `scene.mts::slugAccount` has no such prefix — wiring it in would change every existing account's
  id, a breaking change to any already-persisted save; (3) the module's own doc comment already
  frames it as *documentation* of the pattern `Scene.login` implements ("the same key always
  resolves to the same account... which is the whole of 'token identity'"), not as load-bearing
  code — deleting it loses no behavior, only a stale duplicate. **Action taken**: `src/accounts.mts`
  and `src/accounts.test.mts` deleted; the one dangling comment reference in `client.mts` (line
  761, "see accounts.mts's tokenActorId doc") repointed to `scene.mts`'s own `slugAccount`, the
  code that actually runs. `node --test src/*.test.mts` re-run clean after the deletion (§10).

## 12. Glossary

**Rail** — a maximal straight chain of cells generalizing "row/column" to any tiling
(`tiling-core.mts`). **Chaos Six** — the Ramsey-inspired (not Ramsey-computed, per ADR-2's sibling
honesty pattern) tuned threshold: 6+ concurrently-live specials trigger a guaranteed score-burst.
**Mean coordination** — `2E/N` over the blocker constraint graph, the rigidity-percolation
difficulty dial ramping toward the Phillips–Thorpe isostatic point 2.4. **Lattice Garden** — the
per-chapter completion trophy case (`progression.mts::gardenPieces`).

## 13. Theory binding

Six mechanics are load-bearing on proved or published mathematics, each honestly labeled by
`DESIGN.md`/`README.md` themselves and independently confirmed against the running code for this
document — **note that none of these cite `@561-group/math`**; onestone's math binding is to
general graph-theory/rigidity-theory results (Laman's theorem, the Jacobs–Hendrickson pebble game,
Ramsey's theorem, chromatic number) implemented as this service's own code, not to the owner's
`voidmath`/obsmetrologia/bilattice research package. This is a real, structurally different kind of
"theory binding" than Equivo's or Crucible's (§ fleet audit's cross-service comparison) — worth
naming explicitly rather than letting a reader assume every fleet math-binding section points at
the same corpus.

1. **`validate.mts::pebbleIndependent` is a real, unmodified implementation of the Jacobs–Hendrickson
   (2,3)-pebble game** deciding independence in the generic 2D bar-joint rigidity matroid (Laman's
   matroid, rank `2n−3`) — confirmed by reading the augmenting-path/pebble-collection algorithm
   directly (§ this document's own read of `validate.mts`, above); `lamanCount` is kept specifically
   *because* it is insufficient, to make the double-banana counterexample runnable as a test
   (`validate.test.mts`). **Evidence strength: Strong** — the algorithm is a direct, unadorned
   implementation of a cited, published result, not an analogy.
2. **`meanCoordination`/the level-generation ramp cite the Phillips–Thorpe isostatic point (⟨r⟩ =
   2.4) as a real, provably continuous (second-order) rigidity-percolation transition**, and
   `levels.mts` ramps every chapter's blocker graph toward it — **Strong**, and the claim that this
   produces "no difficulty cliffs by construction" is a direct, checkable consequence of which side
   of 2.4 a level's graph sits on, not a tuning assertion.
3. **`chi(K4)=4` genuinely lower-bounds the palette at king-adjacency junctions** — **Strong** as a
   fact about the palette-size bound, but ADR-2 already corrects the earlier overclaim that the fill
   algorithm itself performs a graph coloring; the honest label is "the bound is real, the mechanism
   citing it is not the theorem's own construction."
4. **Cascade termination's real citation is fall-graph acyclicity, not Knaster-Tarski** — **Strong**
   post-correction (ADR-3), **actively wrong** in `README.md` pending debt item 2's fix.
5. **Chaos Six (threshold 6) is Ramsey-*inspired*, not Ramsey-*computed*** — the engine counts
   concurrently-live specials against a threshold; it never constructs the compatible/incompatible
   edge-2-coloring `R(3,3) ≤ 6` is actually a theorem about. **Evidence strength: disclosed flavor**
   — the module's own header is explicit about this, and this document's independent read confirms
   the code does exactly what the header says (no six-way relation is ever constructed anywhere in
   `engine.mts`).
6. **Ring specials exist because cycles exist on hex/rhombille and provably cannot on square** — a
   real, checkable graph-topology fact (`closesRing`'s bounded-interior test), not a citation to
   external published mathematics but a genuine structural property of the compiled `BoardGeometry`
   itself. **Evidence strength: Strong**, as a fact about the code's own graph, independent of any
   external citation.

## 14. Ludics

- **Core loop.** Swap → match → mint/blast → fall/refill → rescan-to-fixed-point → (level end check).
  Traced in Scenario A. The loop is a conventional match-3 shape at the mechanical level; the
  differentiator is entirely in what geometry the loop runs over (§4).
- **Skill expression.** Two real axes: (1) ordinary match-3 tactical play (setup, combo chaining,
  reading the board) — unchanged by which tiling is active, since `engine.mts` never branches on
  it; and (2) **topology literacy**, a genuinely new axis no other match-3 has: recognizing when a
  hex or rhombille board's cycle structure permits a `ring` special that would be geometrically
  impossible on square, per ADR/§13 item 6. Whether players actually perceive and use this second
  axis is an open, unverified design question — this document states the mechanic is real and
  present in the engine, not that its skill-legibility to a real player has been validated by
  playtesting (no playtest report exists in this repo as of this reading).
- **Session shape.** Bounded — a level, with a fixed move budget (`movesFor`, 18-30 per
  `levels.mts`'s chapter ramp) and a hard win/loss resolution per attempt. This is structurally
  different from flickering-delve's unbounded session and shapes the retention design below toward
  "come back for the next level," not "check in on an always-running system."
- **Retention surfaces.**
  - *Lives* (`economy.mts::tickLives`, cap 5/8, 30-min regen) — real, and per the market teardown
    (`tileslots-market-teardown.md` §2) genuinely "the single most-cited 'predatory friction'
    mechanic in the genre" — this service's lives system is a **hard** gate today (starting a level
    at 0 lives is refused outright), which `TILESLOTS-DESIGN.md` §4.3 itself flags as exactly the
    pattern the market teardown warns against, proposing (not yet implementing) a non-monetary
    "sparks" soft-retry system as the fix (debt item 5).
  - *Star ratings and streak bonus* — real, `winReward`'s bounded quadratic-in-stars formula, capped
    streak window (10 wins) so streak farming plateaus rather than compounding forever — a genuine,
    tested-bounded mechanic (`economy.test.mts`).
  - *Season pass* — real (`passUntil` raises the life cap to 8), but its storefront UI is explicitly
    roadmap ("Settling Pass UI," `ROADMAP.md`) — the economy models the grant; nothing sells it yet.
  - *Lattice Garden* — real, permanent, monotonic trophy tracking (`progression.mts::gardenPieces`),
    no gate, no expiry — a clean instance of the house's "progress is permanent, never a shrinking
    bar" retention posture.
- **Kind-design constraints enforced.** No level-solvability shortcut is *structurally* impossible
  to sell (§8, §13 item 1's evidence) — the fleet's strongest instance of an ethics constraint
  enforced by the type system itself, not merely policy. Lives remain a real, named exception to the
  "no hard gate" ideal, honestly flagged as unresolved debt rather than glossed over.
