# Lantern's face

A static, client-side, zero-dependency SPA that draws the garden compiled by the Lantern
engine (`../src`, see `../DESIGN.md`) and lets a player walk it: review cards to keep rooms
lit, watch the light cone spread and fog, run daily lantern-walks and kata drills. No build
step, no bundler, no framework — plain ES modules loaded straight by the browser.

## Run it

```
npm run build:web   # regenerate web/data/*.json from ../data/world-weiqi.json (see below)
npm run serve:web   # http://127.0.0.1:8080/
```

Env: `PORT` (default `8080`), `HOST` (default `127.0.0.1`).

`index.html` must be served over HTTP, not opened as a `file://` path — the browser blocks
`fetch()` of local files under `file://`, and the map needs to fetch `data/weiqi.json` /
`data/weiqi-layout.json`.

## Tests

```
npm run test:web     # node --test web/test/*.test.mts
npm run verify:web   # build:web, then test:web
```

Two suites:

- `test/parity.test.mts` — asserts the browser-facing ports under `js/engine/` (`srs.js`,
  `lightcone.js`, `kata.js`) are bit-identical to the real `.mts` engine modules they
  transliterate, across a grid of inputs. The ports exist only because a zero-build static
  page cannot load `.mts`; this test is what keeps them honest instead of trusting eyeballs.
- `test/smoke.test.mts` — the required 30-day simulation: drives the real engine directly
  (injected epoch-day timestamps, never `Date.now()`) through an active gate-everything phase
  followed by a lapse, and asserts revealed territory only ever grows while the reachable light
  cone genuinely shrinks on lapse without erasing anything.

## How the pieces fit

```
web/
├── index.html            app shell
├── css/style.css         theme-aware (light/system-dark), prefers-reduced-motion respected
├── server.mjs            zero-dep node:http static file server (this directory only)
├── build/
│   └── build-layout.mts  BUILD-TIME script: reads ../data/world-<wing>.json, runs a
│                         deterministic (fixed seed, fixed iteration count) force-directed
│                         layout, calls the REAL src/kata.mts for auto-hall kata paths, and
│                         writes web/data/<wing>.json (a self-contained copy of the compiled
│                         world) + web/data/<wing>-layout.json (positions + kata paths)
├── data/
│   ├── weiqi.json          (generated — copy of ../data/world-weiqi.json)
│   └── weiqi-layout.json   (generated — room positions + baked auto-hall kata paths)
├── js/
│   ├── engine/            browser ports of the pure engine modules (see parity.test.mts)
│   │   ├── srs.js           FSRS-lite curve + review-update rule
│   │   ├── lightcone.js      light-stage classification + reachable-frontier BFS
│   │   └── kata.js           per-card scoring, belts, ratio→grade (path-gen stays build-time)
│   ├── state.js            localStorage save: versioned schema, streaks/freeze tokens,
│   │                        kata timing history, export/import JSON
│   ├── dailywalk.js         due-set + greedy nearest-unvisited-door route builder
│   ├── gate.js               room-click → gate-pass vs. spaced-review queue decision
│   ├── kata-ui.js            picks each kata room's "next due" card, folds a run into a belt
│   ├── map.js                SVG renderer: room categories, hall enclosures, keyboard nav
│   ├── a11y.js                shared screen-reader live region + reduced-motion helper
│   └── app.js                bootstrap: fetches data, wires map + side panels + review modal
└── test/
    ├── parity.test.mts      js/engine/* vs. the real src/*.mts, see above
    └── smoke.test.mts        30-day territory-grows-then-fogs simulation, see above
```

**Re-run `npm run build:web` whenever the engine recompiles `../data/world-weiqi.json`** — the
face ships its own frozen copy under `web/data/` so the static server never needs to reach
outside its own root, which means that copy goes stale if the source world changes and the
build step isn't re-run.

## What each face-spec item maps to

1. **Map view** — `js/map.js` draws from `data/weiqi-layout.json`'s precomputed positions
   (`build/build-layout.mts`'s deterministic Fruchterman-Reingold layout — same seed, same
   fixed iteration count, every rebuild reproduces the exact same coordinates). Lit rooms glow
   warm, frontier rooms flicker (CSS `@keyframes flicker`, disabled under `.reduce-motion`),
   unreachable rooms are fog silhouettes. Halls render as soft convex-hull enclosures (small
   halls always visible at low opacity; larger halls — several span most of the wing — appear
   on selection from the Halls tab rather than permanently, or they'd cover the whole map).
   Adjacent-to-light fog rooms show name + one-line whisper on hover (the room's `description`,
   markdown-link/citation noise stripped), per the MindMaze spirit.
2. **Gate interaction** — `js/gate.js#buildRoomQueue` decides gate-pass vs. spaced-review vs.
   nothing-due; `app.js`'s review modal (shared by every review flow in the app) shows
   front → reveal → Again/Hard/Good/Easy, applies `js/engine/srs.js#reviewCard`, and on close
   pulses newly-lit rooms (`.room-newly-lit`, CSS animation, skipped under reduced motion).
3. **Daily lantern-walk** — `js/dailywalk.js`: due set = cards with `R(t) < 0.9` unioned with
   cards in currently-reachable rooms at the `dim` stage (the light-cone boundary), ordered by
   a greedy nearest-unvisited-door BFS walk from the last stopping point. Streak + freeze
   tokens: `state.js#touchStreak` (7-day milestone freeze, capped at 3, auto-consumed on one
   missed day), shown in the header.
4. **Kata mode** — `js/kata-ui.js` + `js/engine/kata.js`: pick a kata whose whole path is
   currently reachable, time each room's next-due card through the same review modal, score via
   the DESIGN.md §5 table, award a belt once it's the floor of the last 3 clears
   (`state.js#recordKataRun` tracks `recentRatios`). The kata's own SRS state is scheduled
   separately from the underlying cards' — "one engine, two things it schedules," never a
   second scheduler.
5. **State** — `js/state.js`: `localStorage["lantern:<wing>"]`, `schemaVersion`-gated
   migration chain, export/import via the header buttons (a downloaded/uploaded JSON file).
6. **Accessibility** — every room is a focusable `role="button"` SVG `<g>`; arrow keys move
   focus to the nearest room in that screen direction (`map.js#nearestInDirection`), Enter/Space
   activates; `js/a11y.js` maintains one shared `aria-live="polite"` announcer for room-state
   and review-result changes, and is the single place `prefers-reduced-motion` (or the in-app
   override) is decided.
7. **Static server + smoke test** — `server.mjs` (zero-dep `node:http`), `npm run test:web`
   (see Tests above).
