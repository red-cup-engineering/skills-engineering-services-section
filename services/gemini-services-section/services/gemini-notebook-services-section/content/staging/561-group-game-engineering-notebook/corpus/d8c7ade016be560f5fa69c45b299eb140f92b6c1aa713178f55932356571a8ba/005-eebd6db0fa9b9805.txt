# Semioverse State and Fediverse Client Feasibility

## Current true state

"The 561 Group Semioverse" is not one system. It is a set of disconnected,
unevenly-progressed pieces that share a name by accident more than by
design. The one real, working core is a standards-conformant Fedify-based
ActivityPub server — actor dispatch, inbox/outbox, WebFinger, NodeInfo,
signed delivery — published as `@red-cup-engineering/activitypub-services-section`,
disk version 1.0.15, under active development through 2026-08-17. It has
no live deploy target: no credentials, no reachable server, per the
project's own 2026-08-16 internal audit ("Molt Ledger"), the only genuinely
current, evidence-based status document found in this tree. It documents a
concept of x402 (recognized as a pass-through payload authority inside
nested A2A messages) but does not execute it.

Separately, a real but unfinished Solidity settlement contract
(`SemioticExchange.sol`) and its off-chain builder/replay tooling
(`semiotic-exchange-chain-services-section`) are live and mostly
test-passing, but the contract has never been compiled or deployed to any
chain.

Three other "Semioverse"-named directories — `interactive-semioverse-services-section`,
`agential-semioverse-repository-services-section`, and
`close-semioverse-gap-services-section` — turn out, on exhaustive grep and
read, to be unrelated: they are a personal markdown-vault semiotic
formalism and its documentation tooling, dormant to abandoned, containing
zero ActivityPub/x402/federation/game surface.

So: one real, live, actively-developed federation server; one real, live,
but unconnected-to-chain settlement spec; and three "Semioverse"-named
directories that are false leads. "Currently kind of broken" is accurate
specifically about *deployment* — there is no live instance anywhere — not
about code quality, since what exists mostly runs and mostly passes its
own tests.

The 2026-08-16 Molt Ledger (found while cross-checking, outside the four
assigned sections) rates the ActivityPub service mid-flight and names the
one live blocker to a running instance — which matches the top mechanical
repair item below. It is the closest thing to ground truth this tree
currently contains.

## What got repaired today (2026-08-19)

One repair was made, and its numbers were re-verified by rerunning the
tests fresh before this note was written:

**Corrected a false test-status claim in
`semiotic-exchange-chain-services-section/README.md`.** It previously
claimed all tests in the section failed with `ERR_MODULE_NOT_FOUND` from a
missing `npm install`. That was wrong on every count. Rerunning `npm test`
in each of the three packages today gives:

- `semiotic-exchange-chain-services-section` (top level): **6/6 pass**
- `sovereign-membrane-admission-service`: **6/6 pass**
- `modeled-union-dimension`: **18/19 pass** — the one failure is
  `test/dimension.test.mjs`, `ERR_MODULE_NOT_FOUND` for
  `@red-cup-engineering/typed-resource-catalog/temporal-failure-normalization`,
  a package that has never been written or published anywhere in this
  tree (confirmed again today: `npm view` against the local Verdaccio
  registry 404s, and no such directory exists on disk).

That is 7 test files across the section and its two sub-services, 30 of
31 individual tests passing, and dependencies already installed from
Verdaccio — not an environment gap. The README now states these true,
reproducible counts and attributes the one real failure correctly, to a
genuinely unwritten dependency rather than a setup problem.

As a second spot-check (not previously claimed, run fresh for this note):
`@red-cup-engineering/activitypub-services-section` (disk v1.0.15) —
**39/39 pass**.

Nothing else was changed. No stale `@561-group` package pins
(math/computer/qwzspace) were found anywhere in the four sections examined
— nothing to correct there. No broken import paths were found elsewhere.

## Remaining structural work, in priority order

These are flagged, not attempted — each requires a design or infra
decision, not a mechanical fix:

1. **No deploy target for the live ActivityPub server.** No credentials,
   no reachable host, no HTTPS origin. This is the actual meaning of
   "currently kind of broken": the code runs, but nothing is running it
   anywhere reachable. The legacy VPS package (abandoned 2026-07-19–20)
   has an already-working local-disk KV/queue adapter
   (`SqliteKvStore`/`SqliteMessageQueue` on `node:sqlite`) that solves
   exactly the gap the Molt Ledger names as the active package's
   blocker — porting it forward is the highest-leverage single next step,
   because it is the one thing standing between "no live instance" and "a
   live instance." It was not ported today; this is new integration code,
   outside a strictly mechanical pass.
2. **Registry drift.** `activitypub-services-section` disk is v1.0.15;
   Verdaccio has only v1.0.11 published. A straightforward `npm publish`
   once the package owner wants it public. The Molt Ledger also flags
   roughly 188 unresolved internal-dependency pins tree-wide of the same
   shape — a larger scripted sweep, not attempted here as it wasn't in
   scope for this pass.
3. **`SemioticExchange.sol` has no compile/deploy tooling at all** — no
   Hardhat/Foundry config anywhere in its section or `lib/legacy`.
   Choosing a settlement chain and building deploy tooling is a design
   decision.
4. **x402 execution logic is unexamined.** It lives, if anywhere, in
   sibling packages (`x402-services-section`, `x402-exact-purchase-service`,
   etc.) not touched by this recon. No claim that "x402 works" is
   supportable without a dedicated pass over those.
5. **The sandboxed arrival-handler pattern may be a regression.** The
   legacy server subprocess-sandboxes the customer callback
   (`invokeAcceptedArrivalHandler`: resolved-file/non-symlink check,
   stripped environment, 30s timeout, 16MB output cap). The active
   package instead calls an injected `onActivity` callback directly
   in-process, with no subprocess boundary. Confirmed missing; whether
   this is a deliberate design shift (dependency injection replacing
   process isolation) or an unintentional loss of a security boundary is
   a judgment call for whoever owns the package, not a mechanical fix.
6. **The "Semioverse" name is disconnected from the working code.** None
   of the three dormant/abandoned "Semioverse"-named sections connect to
   the live ActivityPub or chain code, and the live ActivityPub package
   never uses the word "Semioverse" itself. Reconciling the name (or
   accepting the split, e.g. renaming the gaming client's world layer
   rather than the federation server) is a product decision.
7. **The `interactive-semioverse` Python FastAPI/MCP engine** (missing
   `library/` tree, no venv, no deps) is repairable in isolation but
   would restore an unrelated personal skill-runner server, not anything
   feeding the Fediverse-client goal. Lowest priority; likely not worth
   repair effort at all under this goal.

## Gamified Fediverse client — feasibility verdict

**What exists that helps:**
- A real ActivityPub *server*: actor dispatch, inbox/outbox, WebFinger,
  NodeInfo 2.1, signed delivery, via Fedify, currently 39/39 tests
  passing. Genuine federation plumbing, not a stub.
- A partial ActivityPub *sender*: signed-delivery/CLI tooling exists, but
  nothing found anywhere consumes an incoming federated timeline and
  renders or interprets it as anything — game world or otherwise.
- x402: conceptually scaffolded as a payload type that can ride inside a
  federated A2A message, but not executed anywhere examined. No
  challenge/response, no payment verification, no settlement witness at
  the ActivityPub layer.
- Chain settlement: a real, well-specified event-sourced contract with a
  matching off-chain builder and pure-replay reconstructor (30/31 tests
  passing), but never compiled, deployed, or connected to a live RPC.
- Game/world-rendering layer: none. An explicit grep for
  `mmorpg|game`-shaped terms across the "Semioverse"-named sections found
  nothing — no rendering layer, no world model, no game loop anywhere in
  the sections reviewed.

**What is plainly missing:**
- A live, reachable deployment of the ActivityPub server.
- Any x402 payment execution actually wired to that server.
- Any chain deployment of the settlement contract.
- Any code — not a note, not a stub — that turns federated activity into
  a game-world representation.
- A resolved decision connecting "Semioverse" branding to the working
  ActivityPub/chain code, if that connection is wanted at all.

**The smallest honest first step:** port the legacy SQLite KV/queue
adapter into `@red-cup-engineering/activitypub-services-section` and stand
up one real local devbox instance, then verify a live WebFinger → actor →
inbox → outbox round trip against an actual external Fediverse server.
That is mechanical, low-risk, and uses an already-proven pattern from the
legacy code — and it is a hard prerequisite for everything else. There is
currently no live instance to test x402 gating against, none to attach
chain settlement to, and none to render as a game world. Everything else
on this list — x402 execution, chain deployment, the game-rendering layer
itself — is genuine structural design work that should wait until that
one live instance exists, because building any of it against a server
that has never actually federated would be building on an unverified
foundation.
