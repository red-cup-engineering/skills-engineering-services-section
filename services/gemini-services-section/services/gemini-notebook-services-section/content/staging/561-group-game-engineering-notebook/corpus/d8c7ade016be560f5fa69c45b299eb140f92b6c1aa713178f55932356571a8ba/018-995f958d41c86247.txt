# onestone.561.group

A serious browser match-3 whose differentiator is the one thing no incumbent has touched
in a decade: **the grid itself**.

Chapter 1 is exactly what a Candy Crush veteran expects and needs zero onboarding for — a
square 8×8 board, swap-to-match, striped/nova/prism specials, moss/frost/cage/geode
blockers, move-limited levels, three-star rating. Then the hook: the same verbs, the same
engine, a **different real tessellation** each chapter — hex (chapter 2), then a rhombille
board whose three rhombus orientations shade into the tumbling-cubes illusion (chapter 3).
The roadmap ladder keeps climbing from there (see `ROADMAP.md`): Cairo pentagonal →
snub-square → Penrose P2/P3 → the hat/spectre monotile → the Jeandel-Rao 11-tile 4-color
aperiodic Wang set as the citable capstone.

Every tiling compiles down to **one** tiling-agnostic graph engine. There is exactly one
match/cascade implementation in this codebase; it has never seen the word "square" and
never will.

**Branding note:** the storefront/marketing display name is **TileSlots** — the `<title>`,
header wordmark, and every other player-facing string in `src/client.mts` read it. That is
display-only: the service/package name (`@red-cup-engineering/onestone-561-group`), the
`onestone-service` directory, every module/export name, route paths, env vars
(`ONESTONE_PORT`, `ONESTONE_SAVE`, `ONESTONE_LEDGER`), and the `onestone.561.group` domain
framing below are unchanged and un-renamed — "onestone" stays the engineering identity (see
`TILESLOTS-DESIGN.md` §5 for the full rationale and the exact list of what does/doesn't
change).

## Run it

```
node src/server.mts        # http://127.0.0.1:18796/
```

Env: `ONESTONE_PORT`/`PORT`, `HOST`, `ONESTONE_SAVE` (player-meta snapshot path),
`ONESTONE_LEDGER` (audit-journal path), and the payment credentials below. With no
credentials the game is fully playable; payments fall back to a dev mock provider that
clears instantly.

```
npm run check      # node --check src/*.mts  (erasable-syntax-only, strict)
npm test           # node --test src/*.test.mts
npm run verify      # both
```

## Architecture — a tiling-agnostic graph engine, not a grid engine

The one big idea, inherited whole from `src/types.mts`: **the board is a graph, not a
grid**. Every tessellation — square, hex, rhombille today; Cairo, Penrose, hat/spectre,
Jeandel-Rao Wang tomorrow — compiles down to the same `BoardGeometry`: cells with polygons,
shared-edge adjacency, precomputed straight-line `rails`, and a baked `fallTo` gravity
pointer. One match engine (`engine.mts`) consumes that geometry and never branches on
`TilingKind`. Adding a tiling to the ladder means writing a `cells(size): RawCell[]`
producer and nothing else — the match/cascade/scoring/special logic is untouched.

### Module map

| module | role |
|---|---|
| `seed.mts` | deterministic RNG — FNV-1a `hashSeed`, mulberry32 `Rng` (ported from the sibling) |
| `tiling-core.mts` | the geometry compiler: `compileGeometry` turns raw polygons into adjacency, `fallTo`/`fallFrom`, rails, spawn mouths |
| `tiling-square.mts`, `tiling-hex.mts`, `tiling-rhombille.mts` | per-tiling `cells(size)` producers — the only tiling-specific code in the repo |
| `tiling.mts` | registry: `buildGeometry(tiling, size, paletteSize)`, `defaultSize(tiling)` |
| `engine.mts` | the pure match/cascade heart: `spawnBoard`, `findMatches`, `legalMoves`, `applyMove`, `applyBooster` — all pure, input state never mutated |
| `validate.mts` | the math QA oracle: pebble-game solvability, mean coordination, load-bearing check, `validateLevel` |
| `levels.mts` | the 60-level v1 ladder, generated deterministically and validated at build/test time |
| `economy.mts` | wallets, lives, streaks, boosters, SKUs |
| `progression.mts` | unlocks and the Lattice Garden trophy case |
| `accounts.mts`, `ledger.mts`, `payments.mts` | the ported payment boundary — token identity, double-entry audit ledger, mock/stripe/hive providers |
| `scene.mts` | the one stateful piece — per-account meta + active run, subscriptions, atomic persistence |
| `server.mts` | native HTTP/SSE transport |
| `client.mts` | `CLIENT_HTML` — one document, no build, no dependencies |

### Doctrine (inherited from `flickering-delve-service`)

Pure domain modules (`.mts`, each with a `.test.mts`, run under `node --test`, strict
erasable-syntax TypeScript), one stateful scene, one thin native-HTTP transport, a
`PaymentProvider` boundary behind a balanced double-entry ledger with `GET /audit` hledger
export. No runtime dependencies — node builtins only.

**Determinism doctrine**: every board and level is a pure function of seed strings. The
server replays player moves through the exact same pure engine the tests exercise; the
client is presentation only and cannot cheat — it renders `ClientFrame`s and sends
`ClientInput`s, nothing else.

v1 keeps its own atomic-JSON persistence (tmp + rename). FeltOS world integration is
roadmap, scoped to shared events — the sibling's assertion-trace model fits settled
per-move outcomes well; it does not fit per-frame board physics, so v1 does not force the
issue.

## The math is load-bearing (and honestly labeled)

Six places in this codebase, a proved or published result is not flavor text — it is the
actual code path a player's move runs through. Everywhere else in the corpus this design
draws from (the sheaf/H1 material in particular), the material is flavor-naming only, and
that source disclaims truth authority for itself; onestone does not borrow authority it
wasn't given.

1. **Spawn = proper coloring.** Board fill and refill is a rejection-sampled graph
   homomorphism into K_paletteSize (`properColoring_iff_hom`): any color that would complete
   an immediate match against already-placed neighbors is rejected outright. `chi(K4)=4`
   lower-bounds the palette at king-adjacency junctions; square and hex chapters ship 5
   colors, deliberate headroom above that local clique bound.
2. **Level QA runs a real pebble game.** Blocker layouts are checked with the
   Jacobs–Hendrickson (2,3)-pebble game, not a bare edge-count budget — Laman's 2n−3 count
   is necessary but famously not sufficient (the double-banana graph satisfies the count
   while being provably invalid), so `validate.mts` runs the actual independence search.
   No level ships that the math can't certify as solvable.
3. **Difficulty is rigidity percolation.** Each level's blocker constraint graph has a mean
   coordination number; the 20-level chapters ramp it smoothly from ~0.5 toward the
   Phillips–Thorpe isostatic point ⟨r⟩ = 2.4. That transition is provably continuous
   (second-order), which is the honest reason there are no engineered difficulty cliffs —
   not a tuning choice, a consequence of which side of 2.4 a level's graph sits on.
4. **Cascade termination is fall-graph acyclicity, not a depth cap — and not Knaster–Tarski**
   (corrected here from an earlier draft that cited the wrong theorem; `engine.mts`'s own
   header states the correction directly). The settle loop applies its clear/fall/refill
   operator until it is idempotent and stops exactly there — deliberately no `maxDepth`
   anywhere in `engine.mts` — but Knaster–Tarski needs a monotone operator climbing a *fixed*
   lattice, and refill injects fresh RNG-drawn tiles every round, so no such lattice exists
   here. The real reason the happy path always terminates is graph-theoretic:
   `tiling-core.mts`'s `fallTo` requires strictly-greater-y alignment
   (`FALL_ALIGNMENT_MIN`), so the fall graph is acyclic and any one tile can only fall a
   bounded number of times. Per-step score is proportional to settling height times an
   escalating step multiplier, so longer genuine cascades are worth more, not truncated.
5. **Chaos Six is Ramsey R(3,3) ≤ 6.** Six specials concurrently alive on the board
   guarantee a monochromatic triangle in any two-coloring of their pairwise
   compatible/incompatible relation. Six is not a balance number someone picked — it's the
   Ramsey bound, shipped as a guaranteed score-burst event at exactly that count.
6. **Ring specials exist because cycles do.** A match can close a cycle around a cell on
   hex and rhombille boards — that's geometrically impossible on a square grid, where the
   adjacency graph is bipartite-planar in a way that forbids it. The `ring` special is the
   ladder's first "this could never happen on a square board" moment, and it falls directly
   out of which tessellation the board is compiled from.

Nothing above is claimed to make the game *fun* by itself — proved math bounds what the
engine is allowed to generate and how it's allowed to terminate; level design still tunes
goals, moves, and blocker kinds within those bounds.

## Payments & auditability

Three real adapters behind one `PaymentProvider` boundary (`payments.mts`), ported from the
sibling's boundary with onestone naming:

- **mock** — always configured, clears instantly; the default with no secrets set.
- **stripe** — real PaymentIntents over REST, with HMAC-SHA256 **webhook signature
  verification** (env `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`), constant-time compare.
- **hive** — real on-chain settle: the player transfers to `HIVE_ACCOUNT` with the order id
  as memo; confirmed by reading the chain (env `HIVE_ACCOUNT`, optional `HIVE_NODES`), no
  private keys needed to receive.

Every cleared payment posts a balanced double-entry transaction to an **append-only**
ledger (`ledger.mts`). `GET /audit` replays that journal in hledger's plain-text format —
anyone can run it through independent ledger tooling and verify the books balance without
trusting this server's runtime state.

SKUs are bounded by doctrine (`types.mts`'s `Sku.grant`): currency, consumable boosters,
lives, or a time-limited pass — never flat power, and never a level-solvability shortcut,
since solvability is a validated mathematical property of the board (see point 2 above) and
selling around it would falsify the game's own claims about itself.

Identity is token-based (`accounts.mts`) — same near-verbatim port as the sibling's
guest-token model; account-beyond-token-identity (claiming a persistent name) is roadmap,
not v1 scope.
