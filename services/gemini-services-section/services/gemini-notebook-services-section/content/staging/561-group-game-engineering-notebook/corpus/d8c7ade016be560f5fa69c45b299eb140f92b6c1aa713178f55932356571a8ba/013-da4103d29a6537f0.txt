# flickering.561.group — the Gnaw

A next-generation browser **idle-roguelike** on the FeltOS kernel.
Out past the last settlement, the ground opens — a cave the delvers call **the Gnaw**.
You descend the *same* procedurally generated cave everyone descends, for fame, glory, riches, and knowledge; the fauna gets stranger and deadlier the deeper you go, and now and then **Coyote** or **Crow** got there first and left the floor twisted.

It is an idle game, a roguelike, and — its one genuinely new idea — a game about **writing the program that plays it**.

## The arc (playing → strategizing)

1. **Click.** Delve in, attack, descend, retreat.
  Clear floors for essence.
2. **Idle.** Hire an *expedition* — a derivative cascade of torchbearers → pathfinders → cartographers → archivists — that gathers essence while you're away.
  Arm the delver (repeatable attack/health) to reach deeper.
3. **Automate.** Learn *standing orders*.
  Each one — Killing Instinct, Sure Footing, Self-Preservation, Quartermaster, Eternal Return — **folds its manual button out of the UI** and adds a clause to a decision program written in the FeltOS **relational Lisp**.
4. **Rekindle.** When you've fallen deep enough, let the flame gutter out and light it again: prestige collapses the run into **echoes** that buy a permanent production *and combat* bonus, so the next dive reaches deeper than the last.
5. **Strategize.** Once every order is learned, the action bar collapses to a single **Delve** toggle — and the **strategy editor** becomes where you play.
  You tune (or rewrite) the Lisp the tick runs for you each turn.
  The interface stopped being about playing the game; it became about strategizing the play.

## Run it

```
node src/server.mts        # http://127.0.0.1:18795/
```

Env: `FLICKERING_PORT`/`PORT`, `HOST`, `FLICKERING_SAVE` (world snapshot path), `FLICKERING_LEDGER` (audit-journal path), and the payment credentials below.
With no credentials the game is fully playable; payments fall back to a dev mock provider.

```
pnpm run check     # tsc --noEmit (erasable-syntax-only, strict)
pnpm run test      # node --test
```

## Architecture — kernel + purpose-built scene

flickering does not re-implement an engine; it composes the FeltOS kernel and keeps domain logic in pure modules under a thin transport (the 561 doctrine).

- **`@red-cup-engineering/fizzos/world`** — the authoritative state is an immutable assertion world.
  Every scrap of player state is a functional cell (`essence`, `depth`, `gen:*`, `combat:*`, `automation:*`, `echoes`, …) declared on that world, so the trace settles by latest sequence without process-global schema.
- **`@red-cup-engineering/fizzos/lisp`** — the bounded automation/strategy substrate.
  A player's standing orders compile to a Lisp program; the strategy editor lets them rewrite it.
  The tick evaluates it to decide one action — sandboxed (step-budgeted, and we discard the threaded world, so a custom program can *decide* but never *cheat*).
- **`@red-cup-engineering/fizzos/persistence`** — exact world snapshots and atomic JSON persistence.
- **Native Node HTTP/SSE transport** — identity, streaming state, fair queued input, bounded request bodies, security headers, and graceful persistence without a compatibility carrier.
- **Local append-only accounting projection** — validates double-entry balance and emits a portable hledger journal for independent audit.

Pure domain modules (each with tests): `seed` (deterministic RNG), `dungeon` (seeded procgen), `economy` (resources/cascade/cost-curves/combat/formatting), `progression` (unlocks, the autonomy ladder, prestige), `strategy` (run the Lisp decision).
The scene (`scene.mts`) is the one stateful piece — a tick agent pipeline over the world; automation reuses the *same* command handlers manual play does, so there is exactly one implementation of every verb.

## Payments & auditability

The store sells only bounded, time-limited boosts (`Reward = k·CurrentRate·Time` in shape — never flat power that skips tutorial unlocks or prestige).
Three real adapters behind one `PaymentProvider` boundary (`payments.mts`):

- **mock** — clears instantly; the default with no secrets.
- **stripe** — real PaymentIntents over REST, with HMAC-SHA256 **webhook signature verification** (`STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`).
- **hive** — real on-chain settle: the player transfers to `HIVE_ACCOUNT` with the order id as the memo; we confirm by reading the chain (no private keys needed to receive).

Every cleared payment posts a balanced double-entry transaction to an **append-only** journal.
`GET /audit` replays that journal through the standard ledger tooling and reports the independently-computed balances — anyone can verify the books balance.

## Identity: guest, then federate

You play immediately as a **guest** (a client-keyed actor, progress saved server-side).
When you claim a name (`POST /claim` after login), your guest fiber is **migrated** into the durable account via FeltOS's federation move (`exportActor`/`importActor`) — local until you choose to log in.

## Security & performance

Server-authoritative state; the client never asserts resources.
Offline accrual uses server time and is **capped** (anti clock-tampering), simulated as coarse cascade ticks (the honest method for a growing economy).
Player Lisp is bounded by the engine's step budget.
Inputs are validated and flood-controlled (`throttleIntents`).
Webhooks are signature-verified; account secrets are salted hashes; the audit journal is append-only.
The tick touches only potential players, production is analytic/aggregate, the client re-renders lists only when their signature changes, and settling is memoized by the world's `WeakMap`.
