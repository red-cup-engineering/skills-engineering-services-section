## 1. Introduction and goals

flickering (working title "the Gnaw") is a browser idle-roguelike built on the FeltOS kernel
(`@red-cup-engineering/fizzos`) whose one genuinely new idea, per its own `README.md`, is that "the
interface stopped being about playing the game; it became about strategizing the play" — the
autonomy ladder does not bolt autobuyers onto a numbers game, it folds each manual verb into a
clause of a decision program a player later reads and rewrites in FeltOS's own relational Lisp.
This service is the **convention-originating** member of the fleet: `onestone-service/DESIGN.md`
explicitly inherits its doctrine, and `onestone-service/src/ledger.mts`/`payments.mts` are
documented near-verbatim ports of the modules described below (§9 ADR-1). Anything this document
calls "the house pattern" originates here, not somewhere else in the fleet.

## 2. Constraints

Everything in the house standard's §2 applies without local variance, verified directly against
the source read for this document:

- **Determinism.** `seed.mts` is the sole randomness source (FNV-1a `hashSeed` → mulberry32
  `rngFrom`/`rngAt`); a repo-wide grep of `src/*.mts` (excluding `client.mts`, which the standard's
  §2 does not bind — a browser UI's `requestAnimationFrame` loop is not domain logic) turns up
  exactly one `Date.now()` call site, `scene.mts`'s module-level `const nowMs = (): number =>
  Date.now();`, used only as the *default* clock the impure scene reads at construction and passed
  everywhere downstream as a value — never called ambiently inside a pure function. This is the
  constraint working as intended, not a violation: `dungeon.mts`, `economy.mts`, `progression.mts`,
  and `strategy.mts` are all clock-free and RNG-free by inspection.
- **Zero dependencies beyond the pinned FeltOS package and, as of this update, `@561-group/cartridge`.**
  `package.json`'s `dependencies` were `@red-cup-engineering/fizzos@0.2.1` alone at original
  writing; this update adds `@561-group/cartridge@^0.1.0` (from the local Verdaccio registry, via a
  new project-level `.npmrc` scoping `@561-group:registry`), per the house standard's own §2
  exception for vendored `@561-group/*` packages. No `@561-group/math` (or any other math-family
  package) is imported anywhere in this service — §13 is accordingly still omitted below, honestly,
  not filled with a placeholder; `cartridge` is a substrate package, not a theory binding.
- **One stateful scene.** `DelveScene` (`scene.mts`, 672 lines) is the service's one mutable-state
  module; `seed.mts` (62), `dungeon.mts` (182), `economy.mts` (291), `progression.mts` (163), and
  `strategy.mts` (86) are pure, each with a co-located `.test.mts`.

## 3. Context

Deploys as `flickering.561.group` per the vision note's per-game-subdomain convention; not yet
listed with a live entry in `play.561.group/catalog.json` at the time of this document (§11). Money
flows through three real `PaymentProvider` adapters (`mock`/`stripe`/`hive`) behind one boundary
(§8); FeltOS (`@red-cup-engineering/fizzos/{world,lisp,persistence}`) is the one external substrate
this service composes rather than reimplements.

## 4. Solution strategy

"State = world." Every scrap of player progress is a functional cell on the player entity in an
immutable FeltOS world (`essence`, `depth`, `gen:*`, `automation:*`, …), so the game state *is* an
event-sourced audit log with no second persistence model — `snapshot()`/`restore()` are literally
`snapshotWorld`/`restoreWorld` over that one structure (`scene.mts:618-630`). "Automation = Lisp,
decided not executed": a player's owned automation tiers compose into a Lisp program
(`progression.mts::composeStrategy`); the tick evaluates it read-only against the world and takes
only the returned action symbol (`strategy.mts::decideAction`), then applies that action through
the *same* command handlers manual play uses (`scene.mts::runAction` → `command()`) — there is
exactly one implementation of "attack," whether a human clicked it or a player-authored program
decided it.

## 6. Runtime view

**Scenario A — a manual attack that clears a floor and triggers a trickster echo, traced through
the actual code.** `POST /input {token, line:"attack"}` (`server.mts:181-189`) resolves the bearer
token to an actor and pushes `{actor, line}` onto the module-level `queued` array; the next
`setInterval(step, 1000)` tick (`server.mts:109-116`) calls `scene.runTick(intents)`
(`scene.mts:229-244`), which processes manual commands first: `command(actor, "attack")`
(`scene.mts:305-327`) dispatches to `attack()` (`scene.mts:352-370`), which reads `floor-hp` and
the actor's `atk` (via `project()`, `scene.mts:181-211`, itself reading every functional cell and
running it through `economy.mts::avatarStats`), computes `nextFloorHp = floorHp - atk`, and — since
it clears — calls `clearFloor()` (`scene.mts:372-386`), which rounds the floor's `essenceReward`
(computed once, purely, by `dungeon.mts::floorSpec`) by the active boost multiplier, credits
`essence`/`lifetime-essence`, and — if the floor's `trickster.echoes` is nonzero (a `crow-teach`
mark, `dungeon.mts:113`) — credits bonus `echoes` scaled by `economy.mts::echoMultiplier`. Every
mutation is a `this.set(actor, predicate, object)` call, which is `tell(this.world, ...)`
(`scene.mts:177-179`) — the *only* write surface in the whole service, so every state change is,
by construction, an appended fact in the FeltOS trace.

**Scenario B — a fully-automated tick under a player-authored strategy.** With `auto === true` and
at least one automation owned, `automationAgent()` (`scene.mts:253-262`) composes the program
(`progression.mts::composeStrategy` folds owned automations' clauses by priority into `(or
clause… 'wait)`, or returns the player's own custom Lisp verbatim if they've written one), then
calls `strategy.mts::decideAction(program, this.world, actor)` — which evaluates the program with a
1,000-step fuel budget and **discards the threaded world entirely**, keeping only the returned
action symbol, coerced through `normalizeAction` to one of `attack|descend|retreat|rekindle|buy|wait`
(anything else, including a malformed program or a budget exhaustion, silently normalizes to
`wait`). `runAction()` (`scene.mts:265-274`) then calls the *identical* `command()` path Scenario A
used — this is the concrete mechanism behind the module header's claim "a custom strategy can
*decide*, never *cheat*": the Lisp evaluator's own effects are thrown away every single tick: only
a whitelisted symbol crosses the trust boundary.

**Scenario C — a Stripe purchase clearing via webhook, then the boost applying.** `POST
/pay/intent` (`server.mts:190-197`) calls `payments.mts::Payments.intent`, which mints an `Order`
and calls the resolved provider's `createIntent` — for Stripe, a real REST call to
`api.stripe.com/v1/payment_intents` with the order id embedded in `metadata.orderId`
(`payments.mts:90-106`). Stripe's later webhook hits `POST /pay/stripe/webhook`
(`server.mts:208-215`), which calls `Payments.settleStripeWebhook` → `settle(orderId, {payload,
signature})`; `stripeProvider.settle` (`payments.mts:107-116`) verifies the HMAC-SHA256 signature
with constant-time comparison (`verifyStripeSignature`, `payments.mts:121-129`) before ever trusting
the payload, confirms `event.type === "payment_intent.succeeded"` and that the metadata's order id
matches. Only then does `Payments.settle` (`payments.mts:236-259`) check `ledger.has(order.id)`
(idempotency against webhook retries) and post a balanced double-entry `LedgerEntry` — and the
route (not `payments.mts`) applies the resulting `BoostGrant` by calling
`scene.grantBoost(actor, kind, value, durationSeconds)` (`scene.mts:605-614`), which sets a
time-bounded `boost-mult`/`boost-until` cell pair — a rate multiplier, never a flat resource grant,
per the module header's own stated doctrine.

## 7. Deployment view

`node src/server.mts` directly; `FLICKERING_PORT`/`PORT`, `HOST`, `FLICKERING_SAVE` (world snapshot
path), `FLICKERING_LEDGER` (journal path), and the three provider credential sets
(`STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET`, `HIVE_ACCOUNT`/`HIVE_NODES`) — with no credentials
set, both real providers report `configured: false` and every purchase resolves to `mockProvider`
(`payments.mts:210-219`'s `resolve()` fallthrough), so the game is fully playable and testable
without payment infrastructure. Persistence is atomic-JSON via
`@red-cup-engineering/fizzos/persistence`'s `loadJsonSnapshot`/`saveJsonSnapshot`, checkpointed
every 30s and on `SIGINT`/`SIGTERM` (`server.mts:233-255`). **No `DEPLOY.md` exists for this
service** (confirmed: only `DESIGN.md`, `README.md`, `ROADMAP.md` are present) — `onestone-service/DEPLOY.md`'s
Cloud Run pattern (`--max-instances 1`, `--session-affinity`, do-not-configure-real-payments-before-durable-storage)
applies near-verbatim here given the identical single-process-state shape, and writing that
document is the single highest-leverage deployment-readiness gap this service carries (§11).

## 8. Crosscutting concepts

- **Replay verification: RESOLVED 2026-08-19 (this update), with a stated scope boundary.**
  `cartridge-and-energy-bank-spec.md` §1.2's own fit-check named this "the harder case" because
  `DelveScene` folds intent handling into `runTick`'s impure command handlers — that extraction is
  what `src/cartridge.mts` now does: every command handler `scene.mts` runs (`attack`/`descend`/
  `retreat`/`buy`/`automate`/`strategy`/`auto`/`patience`/`rekindle`, plus a new `tick` intent for
  idle production, since a pure function of a log has no ambient "meanwhile") is re-expressed as a
  pure `(state, intent) -> {state, events}` transform over a JSON `DelveState`, calling the exact
  same `economy.mts`/`dungeon.mts`/`progression.mts`/`strategy.mts` functions `scene.mts` itself
  calls — none of those four modules changed. `replay()` delegates to
  `@561-group/cartridge/replay`'s `defaultReplay`; `cartridge.manifest.mts::verify` is the
  standalone verifier entry point. **Scope boundary, stated plainly**: this cartridge covers one
  replayable *run* (essence/depth/combat/automation state); it deliberately does not cover login,
  payments, or offline-accrual (account/session/wall-clock concerns `scene.mts` still owns alone) —
  `DelveScene` itself is unchanged and remains the live service's actual state store. `scene.mts`'s
  own posture (server-authoritative state plus bounded, effect-discarding strategy evaluation,
  Scenario B) is therefore still what the *live* service runs on; the cartridge is a second,
  replay-verifiable path suitable for a future settlement backend, not (yet) a replacement for
  `DelveScene`'s own tick loop. No impurity was found in `economy.mts`/`dungeon.mts`/
  `progression.mts`/`strategy.mts` during this wrap beyond the one already-known, already-injected
  boundary (`strategy.mts::decideAction` needs a FeltOS `World` to evaluate Lisp against —
  `cartridge.mts::worldFor` builds one fresh and purely from `state` on every call, mirroring the
  same effect-discarding posture `strategy.mts` already documented).
- **Ledger invariants: the double-entry balance holds; the payout-never-exceeds-revenue invariant
  does not yet exist here, because there is no payout direction.** `AuditLedger.record` refuses an
  unbalanced entry (`ledger.mts:82-86`); `ledger.test.mts` and `payments.test.mts` exercise this.
  `income:premium`/`assets:cash:{provider}` are the only account families this service posts to
  (`payments.mts:247-255`) — it only ever posts *income*, confirmed directly by reading every
  `record()` call site in `payments.mts`. There is no `liabilities:*`/`expenses:payout:*` posting
  anywhere in this codebase, so the Energy Bank spec's `verifyPayoutInvariant` genuinely does not
  apply yet — this is the specific gap the cartridge/energy-bank spec's §2.1 names when it says
  "none of which flickering-delve's current ledger does today."
- **Ethics as executable tests.** Boosts are bounded by shape (`Reward = k·CurrentRate·Time`,
  §payments header) — `SKUS` (`payments.mts:32-39`) has exactly three entries, every one a
  time-limited rate or offline-cap multiplier, never a flat grant, and `payments.test.mts` asserts
  this shape holds. There is no board/level-solvability analog here (no static content to shortcut)
  — the closest ethical constraint this service enforces is "no boost bypasses tutorial unlocks or
  prestige," stated in `DESIGN.md` and `README.md` but **not currently asserted by any test** — a
  real debt item (§11).
- **Accessibility.** `client.mts` is a 355-line single HTML document; this document does not trace
  its accessibility posture in detail (that belongs to a UI-focused pass, not this architecture
  read), but notes for the record that no automated accessibility test exists in `src/*.test.mts` —
  every one of the 54 passing tests exercises domain logic, none exercise `client.mts` at all.

## 9. Decisions (ADRs), recovered from the code

- **ADR-1: this service is the doctrine originator, not a follower.** Evidence: `onestone-service/DESIGN.md`'s
  own "Doctrine (inherited from flickering-delve-service)" section, and the near-verbatim
  `ledger.mts` port confirmed by direct diff during this document's research (differences are
  limited to doc-comment wording and one commodity-list edit — `payments.mts`/`ledger.mts`'s
  double-entry mechanics are byte-identical in shape).
- **ADR-2: world-as-state, chosen over a second GameState store.** `scene.mts`'s own header states
  the alternative it closed off directly: "There is no GameState store beside the world — the world
  is it, and it is auditable." The evidence this was a real choice, not an accident: `economy.mts`'s
  `GameState` interface exists purely as a *projection* type (`project()`, `scene.mts:181-211`
  rebuilds it fresh from world cells on every call) — nothing persists a `GameState` object across
  ticks, confirmed by grep: `GameState` never appears on the left side of an assignment outside a
  `const`/function-return in any non-test file.
- **ADR-3: automation decides through the same handlers manual play uses, deliberately, to keep
  exactly one implementation of every verb.** Evidence against the alternative (a separate
  "automated attack" code path): `runAction()` (`scene.mts:265-274`) calls `this.command(actor,
  "attack")` — the literal string-dispatch entry point a human's `/input` line also reaches. A
  regression in `attack()`'s combat math cannot silently diverge between manual and automated play
  because there is only one `attack()`.
- **ADR-4: offline accrual reuses the live-tick economy step at coarse `dt`, rejecting a separate
  analytic formula.** `economy.mts`'s own header: "Coarse-tick simulation is the honest method when
  production is non-constant... analytic linear grant would understate it." `offlineAccrual`
  (`economy.mts:236-250`) is implemented as a loop calling `stepEconomy` repeatedly, not a closed-form
  integral — `economy.test.mts` includes a case asserting offline-simulated and online-ticked
  production converge for the same elapsed time, which is the check that would fail if a future
  edit introduced a diverging offline formula.
- **ADR-5 (2026-08-19, this update): the cartridge wrapper adds a new `tick(dt)` intent rather than
  trying to make "idle production" an ambient fact of replay.** Every other intent
  (`attack`/`descend`/...) mirrors an existing `scene.mts` command 1:1; `tick` has no command-line
  equivalent because `scene.mts`'s live tick loop advances production as a side effect of
  `setInterval`, which has no meaning inside a pure function of a logged sequence. The alternative
  considered and rejected: let `replay` accept a `dt` parameter per intent implicitly (e.g. derived
  from each `LogEntry.ts`) — rejected because it would make the *replay engine itself* time-aware
  in a way the rest of the house's determinism discipline forbids (§2); an explicit `tick` intent
  keeps time entirely inside the log, where the replay contract already expects it to live.

## 12. Glossary

**Rekindle** — this service's term for prestige: collapsing a run's essence/generators/depth into
persistent `echoes` (`progression.mts::rekindle`). **Standing order** — a rung of the autonomy
ladder (`AutomationDef`), named for the manual verb it folds away. **Trickster** — a seeded floor
mutator (Coyote robs/gambles, Crow gifts/teaches) that scales a floor's essence reward or grants
bonus echoes (`dungeon.mts::Trickster`).

**Omitted, honestly.** No module in this service imports `@561-group/math` or any other package

## 14. Ludics

- **Core loop.** Click (manual attack/descend/retreat) → idle (the generator cascade runs
  unattended) → automate (standing orders fold verbs into a Lisp clause) → rekindle (prestige) →
  strategize (the endgame: the strategy editor becomes the whole interface). Traced in Scenarios A
  and B above; the loop's final stage is genuinely distinct from a conventional idle game's
  "buy the next autobuyer" loop because the player is editing an executable program, not toggling a
  checkbox — `strategy.test.mts`'s coverage of `validateStrategy`'s parse-error/preview reporting is
  the concrete evidence a real editing surface exists, not only a described one.
- **Skill expression.** Two axes, both real: (1) resource-allocation timing in the early/mid game
  (when to buy which generator tier, per `economy.mts`'s cascade cost curves), and (2) **program
  authorship** in the endgame — writing a Lisp decision program that out-performs the composed
  default is a genuinely different skill than any other fleet game currently asks for. This is the
  service's real differentiator per its own `README.md`'s framing ("a game about writing the program
  that plays it").
- **Session shape.** Unbounded — an idle game's cascade runs whether or not the player is present
  (`offlineAccrual`, capped at `OFFLINE_CAP_SECONDS = 8 * 3600`, extendable by the `long-watch` SKU).
  This shapes the retention surfaces below toward "come back and check in," not "clear today's
  seed."
- **Retention surfaces.**
  - *Offline accrual cap* — real mechanic, not cosmetic: it bounds how much a player can gain by
    staying away, and a purchased boost genuinely extends it (`grantBoost`, kind `"offline"`).
  - *Fame depth* (`fameDepth`, never resets) — real, permanent progress tracking, currently
    surfaced only in `stateFrame` and `status()`'s text, not yet wired to any leaderboard —
    `ROADMAP.md`'s own "Leaderboard" entry names this as next, unbuilt work, honestly.
  - *Boosts* — real, bounded, time-limited rate multipliers, purchasable; never a flat power grant.
  - No streak mechanic, no daily-login bonus, no cosmetic collection layer exists in this service
    today — this is a real absence, not an oversight to gloss over; the vision note's "idle games:
    yes — explore the concept in depth" is aimed at exactly this gap.
- **Kind-design constraints enforced.** No wagering (no chance-scaled reward anywhere in
  `economy.mts`/`payments.mts`, confirmed by reading every SKU and every reward formula). Boosts are
  bounded by shape (§9 ADR discussion) but that bound is not test-enforced against unlock-bypass
  (§11 debt item 3) — stated as policy-only, per the house standard's own instruction to name that
  distinction rather than blur it.

## Roadmap

**Finished means** (per `the-suite-and-the-studio.md` directive 4): complete + polished + no
live-ops dependency + content pipeline documented. flickering-delve meets two of four cleanly
(complete — the full loop through the strategy editor; no live-ops dependency — nothing about play
requires a running team) and is honestly partial on the other two: "polished" is real but unproven
past manual play (no accessibility pass on `client.mts` documented, §8) and "content pipeline
documented" holds for floors (`dungeon.mts`'s tables are the pipeline, deterministic and tested)
but not for whole new biomes/tricksters, which are still hand-edited constant arrays, not a
declared authoring pipeline the way `levels.mts`'s generator is for onestone.

**Now** (verified 2026-08-19, re-verified after this update — §10): the full
click→idle→automate→rekindle→strategize loop, 63/63 tests passing (54 original + 9 new), three
real payment adapters with webhook signature verification, guest→account federation via FeltOS
entity export/import, deterministic shared procedural cave generation, and — new this update — a
real, replay-verifiable `@561-group/cartridge` adoption (`src/cartridge.mts`/`cartridge.manifest.mts`),
scoped to one run (§8, §9 ADR-5).

**Next** (scoped, buildable with no new design decision required):
- Write `DEPLOY.md`, porting `onestone-service/DEPLOY.md`'s Cloud Run pattern.
- Add `seed.test.mts` and a `server.mts` smoke test (both concrete, scoped, no design work needed).

- Wire `DelveScene`'s own live tick loop to reuse `cartridge.mts`'s pure command handlers directly
  (today the two are parallel implementations of the same rules, both correct by test but not

**Later** (blocked on a decision or dependency that doesn't exist yet):
