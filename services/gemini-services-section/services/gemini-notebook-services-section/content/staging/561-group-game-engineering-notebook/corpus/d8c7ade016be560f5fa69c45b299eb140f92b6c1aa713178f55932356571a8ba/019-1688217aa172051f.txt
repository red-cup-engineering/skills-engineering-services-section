# TileSlots — parity + juice design spec

Companion to `DESIGN.md` (module contracts) and `ROADMAP.md` (tessellation ladder). Where
those two describe what onestone *is*, this document specifies what three parallel
implementation agents build next to close the gap the market teardown identifies:
[`tileslots-market-teardown.md`](../../../../../content/text/documents/articles/notes/tileslots-market-teardown.md)
(§ numbers below refer to it). Read that document before this one — every claim here traces
to a specific section of it, cited inline.

**Status quo, precisely.** `node --test src/*.test.mts` is green at **191/191** before this
document changes a single line of code — that is the baseline every implementation PR must
preserve. Two things the teardown calls table-stakes are **already fully shipped**, not
aspirational: the topology-native special-piece system (`types.mts`'s `SpecialKind`,
`engine.mts`'s `findMatches`/`fireSwapSpecials`) and provable level solvability
(`validate.mts`'s pebble-game oracle, `levels.mts`'s ⟨r⟩ ramp). Section 3 of this document is
therefore a *specification of the existing system in the teardown's vocabulary*, not a new
design — implementers should not re-derive special-piece rules from the teardown's illustrative
tier names; the engine's own names (`striped`/`nova`/`prism`/`ring`) are the source of truth.
The one confirmed, material gap is rendering (§5 below): the client renders the board as
inline SVG + CSS-transition DOM nodes, which the teardown flags by name as the pattern that
"degrades badly" and is "the worst case" for cascades. Sections 1–2 replace that renderer.

Everything below is additive to the shipped engine (`engine.mts`, `tiling-core.mts`,
`types.mts` are **not modified** by this spec) except where marked "new field" in §4, which
proposes one, clearly-scoped `PlayerMeta` extension for a future pass.

## 1. Juice spec — cascade feel

### 1.1 What's being replaced

Today (`client.mts`): each `CascadeStep` drives two fixed `setTimeout` waits — `FLASH_MS = 45`
then `STEP_MS = 95` — via `runStep`/`animateCascade` (client.mts ~L779–807). Movement is a
CSS-transition on `transform` (`moveTileEl`, ~L754), triggered inside a double
`requestAnimationFrame` to force a style flush, easing `var(--spring)` =
`cubic-bezier(.34,1.56,.64,1)`. This is not delta-time rAF tweening — it's discrete
setTimeout-gated CSS animation, and every tile in a step moves for the same fixed duration
regardless of how far it travels. That's adequate on today's small boards but is exactly the
architecture the teardown's §5 performance section (delta-time rAF, never `setInterval`/fixed
timeout chains) says to avoid, and it has no room for the layered feedback stack §1 describes
(particle, escalating audio, screen shake) without stacking more ad-hoc timers.

### 1.2 New model: one rAF loop, tween list, delta-time

Replace the `setTimeout` chain with a single driving loop:

```
interface Tween { id; kind: 'fall'|'clear'|'spawn'|'shake'|'popup'|'particle'; t0; dur; from; to; ease; done? }
function tick(now: DOMHighResTimeStamp) {
  const dt = now - lastNow; lastNow = now;
  activeTweens = activeTweens.filter(advance(dt));   // pure list transform, see §2.3
  draw(activeTweens);                                 // canvas paint, see §2
  if (activeTweens.length) requestAnimationFrame(tick); else loopRunning = false;
}
```

A `CascadeStep` is decomposed into tweens up front (not awaited step-by-step): clears, falls,
and spawns for one step all start together, each tween's `dur` computed from its own kind (see
table below), and the *next* step's tweens are enqueued only once every tween belonging to the
current step has reported `done` — this preserves the existing step-sequential semantics
(`CascadeStep[]` order must stay visible, matches/specials/blockers resolve in-order) while
letting individual tiles in the same step run independent, geometry-scaled durations instead of
one shared fixed `STEP_MS`.

### 1.3 Settle rules per tiling family

The engine does **not** need per-tiling settle logic — `compileGeometry` (`tiling-core.mts`)
already bakes one uniform `fallTo`/`fallFrom` graph for every tiling (never branches on
`TilingKind`), and `applyMove`'s cascade walks that graph identically regardless of geometry.
What genuinely differs per family is *only* the renderer's presentation of that same
`falls: {from,to}[]` array, because the three shipped tilings differ in cell geometry:

| Family | `fallTo` edge shape | Renderer rule |
|---|---|---|
| **Square gravity** (chapter 1) | Unit-length, strictly vertical (dot(+y) > 0.25 dead zone, but on a square lattice every valid edge is exactly vertical) | Classic straight drop. Stagger tiles within one falling column by their `fallTo`-chain depth (mouth = depth 0), 12 ms per depth step, so a 3-cell drop cascades top-to-bottom instead of teleporting in lockstep. |
| **Hex slide** (chapter 2) | Unit-length but not vertical in screen space — pointy-top axial hex `fallTo` picks the most +y-aligned of up to 6 neighbors, so chains visually zigzag left/right while descending | Same depth-based stagger as square, but the per-tile translation is the *actual* `(toCell.cx,toCell.cy) − (fromCell.cx,fromCell.cy)` vector (already what `moveTileEl` computes) — no special-casing needed, this row exists to document that "slide" is an emergent property of the baked geometry, not a distinct rule. |
| **Rhombille today / aperiodic next (Cairo, Penrose, hat)** | Unit-length within rhombille (`tiling-rhombille.mts` emits unit-scale rhombi), but **future aperiodic prototiles are not uniform size** — a `fallTo` edge's geometric length varies per source/target cell pair | **Duration must scale with geometric fall distance**, not stay fixed. Compute `dist = hypot(dx,dy)` per fall and set `dur = clamp(BASE_FALL_MS * (dist / unitCellSpan), MIN_FALL_MS, MAX_FALL_MS)` (table below) rather than one constant duration for every fall in a step. Rhombille ships uniform rhombi today so this rule is presently a no-op there — it becomes load-bearing the moment a Cairo/Penrose/hat cell producer lands, so implement it now rather than retrofitting it under the Layer 6c aperiodic work. |

"Nearest-slot" settle (aperiodic boards where a cell may have several plausible `fallTo`
candidates) is already resolved at compile time by `tiling-core.mts`'s nearest-center
contention rule — the renderer never re-decides a fall target, it only animates the one the
engine already picked. No aperiodic-specific renderer branch is needed beyond the
distance-scaled duration above.

### 1.4 Timing / easing parameter table

All durations in ms, all distances in **board units** (the same coordinate space as
`Cell.poly`/`cx`/`cy` — e.g. one square cell edge = 1.0 unit), all easing functions given as
the cubic-bezier already defined in `client.mts`'s `:root` (`--spring`, `--ease`) so canvas-side
JS tween math and any remaining CSS (HUD chrome, sheets) stay visually consistent.

| Layer | Trigger | Duration | Easing | Notes |
|---|---|---|---|---|
| Flash (pre-clear) | `step.cleared` cells, `step.fired` cells | 90 ms | `--ease` (`cubic-bezier(.22,.9,.3,1)`) | Brightness/saturation pulse in place before removal — keeps today's `flashClear`/`flashFire` semantics, ~2× today's 45 ms `FLASH_MS` so the particle burst (below) has room to read before the tile vanishes. |
| Clear (shrink-out) | same cells, starts when flash ends | 140 ms | ease-in-cubic `cubic-bezier(.55,0,.85,.35)` (new — old `clear-shrink` used `--ease`, an ease-*out*, which is backwards for a disappearing object: accelerate away, don't decelerate into nothing) | Scale 1 → 0.15, opacity 1 → 0, plus 6° random rotation jitter for "shatter" read. |
| Fall (settle) | `step.falls` | `BASE_FALL_MS = 220` × `dist/unitCellSpan`, clamped `[MIN_FALL_MS=120, MAX_FALL_MS=340]` | Ease-out-cubic for the first 85% of travel (`cubic-bezier(.16,.84,.32,1)`), then an **overshoot-settle**: travel to 106% of target offset by 92% of `dur`, then spring back to 100% over the remaining 8% (`--spring`) | Directly implements teardown §1's "ease-out … overshoot/settle reads as alive" — the settle bounce is the single highest-value juice change per the cited GDC/Juice-It-or-Lose-It framing. |
| Spawn (pop-in) | `step.spawned` | 260 ms | `--spring` | Same beat as today's `pop-in` keyframe (scale .2→1.12→1, translateY(-14 board-units-equivalent)→0), kept because it already reads well; just re-driven by the rAF tween list instead of a CSS `@keyframes` so it can be delta-time-scaled alongside falls. |
| Per-tile stagger | within one step, by `fallTo`-chain depth | +12 ms per depth level, cap +96 ms (8 levels) | — | Prevents a tall single-column drain from reading as one instantaneous jump-cut. |
| Inter-step gap | between cascade steps | `max(40, 260 - 18*stepIndex)` ms, floor 40 ms | — | Escalating cascades should visually *speed up*, not stay metronomic — reinforces the combo-audio pitch-rise below and shortens dead time on long chains without ever going faster than legible (40 ms floor ≈ 2 frames at 60 fps). |
| Screen shake | any step where `step.cleared.length >= 8` OR a special fires OR `chaosSix` | amplitude `min(0.06 * sqrt(cellsResolved), SHAKE_MAX = 0.18)` board-units, decaying `amplitude * e^(-t/60ms)` | — | Budget is deliberately small (0.18 board-units ≈ well under one cell width) — shake reinforces big moments without becoming disorienting; **must be skipped entirely when `matchMedia('(prefers-reduced-motion: reduce)')` is true**, falling back to a single 1-frame flash-white overlay instead. |
| Combo audio pitch | per cascade step index within one settle | base 220 Hz, `+80 Hz * min(stepIndex, 6)` (caps at step 6, matches `chaosSix`'s 6-special threshold as the natural ceiling) | — | See §1.5. |

`BASE_FALL_MS`/`MIN_FALL_MS`/`MAX_FALL_MS`/`SHAKE_MAX` above are named constants so a future
tuning pass (post-playtest, per teardown §1's Raviosoft citation on ±2–3-unit tuning) is a
one-line edit, not a re-derivation.

### 1.5 Audio — WebAudio-synthesized, zero assets

No audio files ship (repo doctrine: zero external deps, no binary assets to maintain across a
60-level, 3-tiling ladder). Every cue is a short `OscillatorNode`/`GainNode`/`BiquadFilterNode`
graph built and torn down per event through one shared `AudioContext`, created lazily on first
user gesture (autoplay-policy compliant) and reused for the session.

| Event | Waveform | Frequency | Envelope (attack/decay, ms) | Gain peak | Notes |
|---|---|---|---|---|---|
| Tile clear ("pop") | `triangle` | 220 Hz base, `+80 Hz` per concurrent cascade step (table above) | 4 / 90 | 0.22 | One voice per *step*, not per tile — N simultaneous clears in one step still produce one pop, pitched by step index, or the stack becomes noise on an 8×8 board. |
| Special fire ("boom") | `sine` sweep 180→60 Hz over the decay + a 30 ms `square`-wave click at attack | 2 / 160 | 0.30 | Per `step.fired` entry; if 2+ specials fire in the same step (a compound swap, e.g. `striped+striped`), stagger their booms 25 ms apart rather than summing gain, avoiding clipping. |
| Chaos Six flourish | 3-note `sawtooth` arpeggio (330/440/550 Hz, 60 ms apart) through a lowpass sweeping 400→4000 Hz | 5 / 300 total | 0.28 | Fires once per settle where `SettleResult.chaosSix` is true — the existing `#chaos-flourish` CSS burst stays as the visual pairing, this is its audio half (currently silent). |
| Blocker break (moss/frost/cage/geode) | `noise` burst (buffer of random samples through a bandpass centered on 900/1400/500/700 Hz respectively — moss=soft/high, cage=metallic/mid, geode=dull/low) | — | 3 / 70 | 0.16 | Distinct timbre per blocker kind reinforces the visual glyph without needing the player to read text. |
| Illegal swap | `sine` | 140 Hz | 2 / 60 | 0.12 | Short, low, unobtrusive — the "nope" cue, distinct from every clear/fire sound above by being the only one that *falls* in pitch and never repeats/escalates. |

All gain nodes route through one master `GainNode` exposed as a single mute toggle in the HUD
(persisted client-side; no server round-trip needed). Simultaneous-voice ceiling: cap concurrent
active oscillators at 8; beyond that, newest-event-wins (older voices are given a 15 ms
fade-out and stopped) to bound CPU on a long chain reaction.

### 1.6 Particle burst and score popup

- **Particle burst**: on each `step.cleared` cell, spawn 4–7 small quads (count scales with
  `stepIndex`, capped at 10) at that cell's `(cx,cy)`, initial velocity radiating outward at a
  random angle within ±30° of "away from board center," speed 0.9–1.6 board-units/s, gravity
  0.4 board-units/s² pulling toward `+y`, lifetime 340 ms, color = the cleared tile's palette
  color (`PALETTE[color % PALETTE.length]`, matching `client.mts`'s existing 5-color table so
  particles never introduce an inconsistent palette), fading opacity linearly over the last
  120 ms of lifetime. Rendered as filled rects (cheapest primitive) on the animated-tile canvas
  (§2), never a separate canvas — they share the same dirty-rect region as the clearing tile.
- **Score popup**: one floating "+N" text per step (not per cell — matches the audio pop
  design, avoids clutter), spawned at the step's `centerOf` cell (reuse `engine.mts`'s
  `centerOf`-equivalent: the origin cell already carried on the step's dominant `MatchGroup`,
  or the mean of `step.cleared` if ambiguous), rises 0.6 board-units over 520 ms with ease-out,
  font-weight bold, fades in over the first 60 ms and out over the last 150 ms. Value shown is
  `step.score` (already computed by the engine — no client-side recomputation, keeping score
  display provably consistent with the authoritative server value in `ClientFrame.score`).

## 2. Renderer — layered Canvas 2D

### 2.1 Why (recap of the confirmed gap)

The teardown is explicit and near-unanimous on this point (§5): "SVG degrades badly past a few
thousand DOM nodes," "cascades are the worst case" for DOM/CSS-transform tiles, "Canvas (2D) is
the standard choice for match-3-scale boards." The current client is exactly the pattern
flagged: one `<polygon>` per cell plus one `<g class="tile">` DOM node per tile
(`buildBoardShell`, `makeTileEl`, `client.mts` ~L674–736), animated via CSS transitions and
class toggles. At today's board sizes (square 8×8 = 64 cells; hex/rhombille radius-4/3 patches,
low hundreds of cells) this has not caused a measured problem, but it is architecturally the
thing the teardown says not to build, and it has no headroom for the Cairo/Penrose/hat/Wang
roadmap chapters, which the repo's own `ROADMAP.md` already commits to. This section replaces
it now rather than after a tiling ships that makes the gap visible.

### 2.2 Layer architecture

Two stacked `<canvas>` elements, same CSS `position: absolute; inset: 0`, sized to the board's
container with `devicePixelRatio` backing-store scaling (`canvas.width = cssW * dpr`,
`ctx.scale(dpr, dpr)` — SVG's `viewBox` gave this for free; canvas does not, so it must be
handled explicitly on resize and on `window.matchMedia('(resolution: ...)')` change):

```
<canvas id="lattice-canvas">   <!-- static: cell polygons, gridlines, blocker glyphs-behind-tile if any -->
<canvas id="tile-canvas">      <!-- animated: tiles, particles, score popups, screen-shake transform -->
```

- **`lattice-canvas`** is repainted only when the board geometry changes (level load, resize,
  theme/palette change) — never per animation frame. It draws `geom.cells[].poly` as filled/
  stroked paths and, for rhombille, the `shade`-driven cube-illusion lightness steps (today's
  `colorForCell(color, shade)` logic, ported verbatim). Because it repaints on an *event*, not a
  frame, the dirty-rect discipline in §2.4 does not apply to it — it always does one full clear
  + redraw, and that is fine because it happens rarely.
- **`tile-canvas`** is repainted every rAF tick *while `activeTweens.length > 0`*, and is
  otherwise left untouched (loop stops entirely when idle — §1.2's `tick` function does not
  reschedule itself once nothing is animating, so an idle board costs 0 CPU per frame, not a
  wasted 60 Hz clear/redraw of a static scene).

### 2.3 The pure state-projection function (the testable seam)

`node --test` runs under Node, which has no `<canvas>` — any function that touches a
`CanvasRenderingContext2D` cannot be unit-tested the way `engine.test.mts` tests `engine.mts`.
The fix is the same discipline the rest of the repo already follows (pure core, thin stateful
shell): split the renderer into a pure projection function and a thin imperative paint step.

```ts
// Pure. No canvas, no DOM, no Date.now() — takes time as a parameter. Fully unit-testable.
export interface RenderCommand {
  kind: 'tile' | 'particle' | 'popup' | 'shakeOffset';
  cell?: CellId;
  x: number; y: number;       // board-unit coordinates (lattice-canvas's own coordinate space)
  scale: number; rotation: number; alpha: number;
  color?: ColorId; special?: SpecialKind;
  blockers?: { moss: boolean; frost: boolean; cage: boolean; geode: number };
  text?: string;               // popup only
}

export function projectFrame(
  geom: BoardGeometry,
  tiles: readonly Tile[],
  tweens: readonly Tween[],
  now: number,
): readonly RenderCommand[]
```

`projectFrame` owns all the tween-interpolation math (easing curve evaluation, overshoot-settle
computation, particle position-at-time, popup position-at-time, shake-offset-at-time) and
returns a flat, declarative command list — nothing more than "draw this glyph at this
board-unit position with this alpha/scale/rotation." `engine.test.mts`-style tests can feed it a
synthetic `Tween[]` and a fixed `now`, then assert on the returned `RenderCommand[]` shape
(positions at a known fraction of a tween's duration, alpha at a known fade point, etc.) with
plain `node:assert/strict` — exactly like every other pure module in `src/`, and exactly what
the market teardown's "frame-rate-independent tweening... analytic tween functions" (§5)
implies is possible: analytic functions are the ones you can assert on without rendering a
frame.

The imperative half — `paintFrame(ctx, geom, commands)` — is a thin loop over
`RenderCommand[]` calling `ctx.fillPath`/`drawImage`/`fillText` per command, using the
precomputed `Path2D` cache (§2.5). It is intentionally too dumb to need its own tests beyond a
smoke check that it doesn't throw; all the logic worth asserting on lives in `projectFrame`.

### 2.4 Dirty-rect redraw

Each rAF tick computes the **union bounding box** (in board units, padded ±0.3 units for
particle/overshoot spill) of every cell touched by an active tween this frame — falling,
spawning, clearing, plus any live particles/popups. `tile-canvas` clears and redraws *only*
that rect (`ctx.clearRect`/`ctx.save(); ctx.beginPath(); ctx.rect(...); ctx.clip(); … redraw …
ctx.restore()`), not the whole canvas. Any tile whose cell polygon overlaps the dirty rect but
is itself idle this frame is still redrawn from the tile cache (canvas has no partial-pixel
persistence the way "leave old pixels alone" implies for non-overlapping regions — but tiles
that don't overlap *any* active tween's rect are skipped entirely, which is the actual win on a
board where one column is cascading and the rest is static). This directly implements the
teardown's named pattern ("dirty-rectangle redraw: only clear/redraw the changed bounding box
per frame — critical with several simultaneous cascade chains on a large aperiodic board," §5)
and is exactly why multiple simultaneous cascade chains (a real scenario on any board with 2+
independent gravity mouths) stay cheap: each chain's dirty rect is independent, and their
union — not a full-canvas clear — is what gets redrawn.

### 2.5 Precomputed geometry — "never recompute tiling math per frame"

At geometry load (once per level, not per frame):

- One `Path2D` per cell, built from `cell.poly`, cached in `Map<CellId, Path2D>` — reused by
  both `lattice-canvas` (cell fill/stroke) and `tile-canvas` (tile face fill, clipped to the
  cell's own shape so non-square/rhombille tiles don't paint outside their polygon).
- One `Path2D` per **glyph** (the five color-blind shape glyphs already defined as SVG
  `<symbol>`s — `glyph-shape-0..4` — plus the four special glyphs `glyph-striped/nova/prism/
  ring` and the blocker glyphs moss/frost/cage/geode), parsed once from the same path data the
  SVG symbols already encode (the symbol `<path>`/`<polygon>`/`<circle>` definitions in
  `client.mts`'s inline `<svg>` sprite sheet translate directly to `Path2D` constructor calls —
  this is a straight port, not a redesign, so the existing color-blind-accessible glyph set
  (§ DESIGN.md's "distinct lightness + glyph per color at minimum on specials") carries over
  unchanged). Striped's per-cell rotation (`railAngleForCell`, reading two actual rail-cell
  centers rather than a fixed per-family lookup table — already correct for every tiling by the
  existing code's own reasoning, see client.mts's comment at that function) is applied as a
  `ctx.rotate()` around the cell center at paint time, not baked into the cached path.
- Rhombille's cube-illusion shading (`colorForCell` combined with `cell.shade`) is precomputed
  into a small `color × shade` lookup table (5 colors × 3 shades = 15 fill-style strings) rather
  than recomputed per tile per frame.
- This cache is invalidated and rebuilt only on level load / geometry change — never touched
  inside the rAF loop. This is the literal instruction from the teardown's §5 bullet
  ("precompute/cache expensive geometry... once at level load; never recompute tiling math per
  frame") and is what makes it safe to add Penrose/hat prototile paths later without a
  per-frame cost regression: a baked-offline deflation asset (per `ROADMAP.md`'s Penrose/hat
  entries) is loaded once and Path2D-cached exactly like today's three `cells()` producers'
  output is, through the same cache.

### 2.6 Migration note

`buildGeometry`/`spawnBoard`/`applyMove` and everything server-side are untouched — this is a
client-only, `src/client.mts`-scoped rewrite. `ClientFrame`/`ClientInput` (the wire contract)
do not change shape. The one-file-no-build doctrine holds: `projectFrame`/`paintFrame`/the
`Path2D` cache all live inside `CLIENT_HTML`'s inline `<script>`, same as today's SVG code —
"layered Canvas 2D" describes the runtime architecture inside that one document, not a new
build step or dependency.

## 3. Special pieces — already shipped, documented in the teardown's vocabulary

The teardown calls topology-native specials TileSlots' "hardest and most interesting" design
problem (§1) and the top "beat it" differentiator (§6.2, item 4: "a content moat competitors
can't copy without solving the same geometry"). This is done, not proposed: `types.mts`'s
`SpecialKind` and `engine.mts`'s `findMatches`/`fireSwapSpecials` implement exactly this, tested
at 191/191 today. This section is the parity check — mapping the shipped system onto the
teardown's own tier framing precisely enough that no implementation agent re-derives or
duplicates it.

### 3.1 Formation conditions (from `engine.mts::findMatches`, verified against source)

| Tier (teardown framing) | Engine name (`SpecialKind`) | Formation | Topology note |
|---|---|---|---|
| **Tier 1 — LINE** | `striped` | Rail run of **exactly 4** same color (`runLen === 4` in the rail scan) | "Lane," not "row/column": a `Rail` is a maximal straight chain per `tiling-core.mts`'s direction-bucket walk, so this is already the topology-native lane the teardown asks for on hex (3 rail families) as much as square (2 families) — no separate hex definition needed. |
| **Tier 2 — BLOOM** | `nova` | Same-color **blob of 5+ containing a junction cell** (a member with 3+ in-group neighbors, `findJunction`) | Fires as the **1-ring neighborhood** of the junction cell (`novaBlast`: `[cell, ...cell.neighbors]`) — note this is radius-1, not the "radius-2 closed neighborhood" a naive reading of "wrapped candy" might suggest; radius-1 was chosen and tested against the actual variable-degree adjacency of hex/rhombille cells (a rhombille cell's 1-ring is already a meaningfully large blast relative to board size), and changing it is an `engine.mts` change out of this document's scope, not a renderer/juice change. |
| **Tier 3 — PRISM (line-form)** | `prism` | Rail run of **5+** same color (`runLen >= 5`) | Clears **every cell of one color, board-wide** (`prismBlast`) — the direct color-bomb analog, and topology-agnostic by construction (it targets by color, not shape, so it needs no per-tiling variant at all). |
| **Tier 3 — PRISM (cycle-form)** | `ring` | Any match group (rail *or* blob) whose cells close a topological cycle around one non-member cell — `closesRing`'s bounded-interior test: some cell outside the group has *every* neighbor inside the group | **Geometrically impossible on square** (a cell's 4 orthogonal neighbors are pairwise non-adjacent, so no connected match can contain all of them without also containing the enclosed cell itself) — first becomes reachable on hex (chapter 2), per `DESIGN.md`'s own framing: "the ladder's first 'this could never happen on a square board' moment." On fire, converts the derived interior cell to a fired prism (`ringInterior` + `prismBlast`). |

`mints: 'none'` (plain 3-run/3-blob, no special) is the implicit fourth row — included here
only to note that a bare match-3 never mints, consistent with the genre baseline the teardown
takes for granted.

### 3.2 The combo matrix (from `engine.mts::fireSwapSpecials`, verified against source)

Only swaps where **both** sides carry a special are "compound" in the strictly-better-than-sum
sense the teardown calls for (§1: "combos multiply the effect... each pair strictly better than
the sum of parts"). Single-special swaps (one side special, one side plain) fire that one
special solo via `fireSolo`, with one contract-documented exception: a **prism swapped against
a plain tile clears every cell of the *plain tile's* color** (not the board's most-common
color — that fallback is reserved for a prism fired indirectly, by a chained blast, where there
is no "other side of the swap" to read a color from).

| A special | B special | Result | Engine behavior |
|---|---|---|---|
| `striped` | `striped` | Both full rails clear | `railBlast(aCell) ∪ railBlast(bCell)` |
| `striped` | `nova` (either order) | Every cell in the nova's 1-ring gets its own rail cleared — a "plus/cross" pattern generalized to whatever the local rail geometry is | `novaBlast(novaCell)` then `railBlast` from each resulting cell |
| `prism` | `prism` | **Entire board clears** | every tile id added to the blast set |
| `prism` | `striped` (either order) | One board color, chosen deterministically from the seeded draw stream (`makeRng(seed#drawN)`, so replays stay exact), has every tile of that color turned into a fired `striped` — i.e. every tile of that color clears its own rail | `prismBlast(color)` cells each independently `railBlast`ed |
| any other pair (`nova+nova`, `prism+nova`, `ring`+anything, …) | — | **Not compounded** — each side fires its own solo blast independently, deterministically, nothing silently dropped | Explicit engine.mts comment: "not in DESIGN.md's compound table... each side just fires its own solo blast independently — total, sane, and never silently drops a special the player swapped." |
| `prism` | plain tile | Every cell of the **plain tile's** color clears | `prismBlast(tiles, otherColor)` |
| any special | plain tile (non-prism) | That one special fires solo at its own cell | `fireSolo` |

Implementation agents extending this table (e.g. a future `Duality Bomb` per `ROADMAP.md`'s
Cairo chapter) add a named branch to `fireSwapSpecials` and a corresponding row here — the
"everything else falls through to independent solo fire" default means an unhandled new
`SpecialKind` combination is never a silent bug, only a missed juice opportunity, which is the
correct fail-safe direction.

### 3.3 What this pass adds on top (juice only, no engine change)

- Per-special sound cue and particle-color mapping (see §1.5/1.6) keyed off `step.fired[].kind`
  — `nova` gets a wider/rounder particle spread (matches its radial blast shape), `striped` gets
  a directional streak of particles along the rail's actual angle (`railAngleForCell`, already
  computed for the glyph rotation — reused, not recomputed), `prism`/`ring` get the Chaos-Six-
  style arpeggio scaled down (a "mini fanfare") since a board-wide or cycle-closing clear is
  already the game's biggest single-swap moment short of Chaos Six itself.
- The `Path2D` glyph cache (§2.5) is the only renderer-side change to how specials are drawn;
  their visual silhouettes (already distinct per the teardown's "legible at a glance" principle
  — striped bars, nova ring, prism star, ring circle) are ported unchanged.

## 4. Saga map — level path, stars, soft attempts, earnable boosters

### 4.1 Path structure

Chapters already map 1:1 onto tilings (`LevelSpec.chapter` 0/1/2 = square/hex/rhombille,
`levels.mts`, 20 levels each) — that axis needs no new design. What's specified here is the
map's *visual/navigational* structure, which today is a flat chapter/level list per
`DESIGN.md`'s client contract ("chapter/level map (3 chapters, stars, locks...)"). Per the
teardown's §2 framing ("linear-but-branching path... cheap to build, huge retention ROI...
directly portable to any tiling: the map itself needn't be tiling-dependent"):

- Within each 20-level chapter, every **5th level is a branch node**: levels `{5,10,15,20} +
  chapterOffset` present the player with **two parallel 1-level spurs that rejoin** before the
  next branch node (e.g. levels 6a/6b, both leading into 7) rather than one linear level. Spurs
  reuse `levels.mts`'s existing deterministic-by-id generation — a spur is just two `LevelSpec`
  ids instead of one at that slot, both still individually pebble-game-validated by
  `validateLevel`, so this is a level-count/id-numbering change in `levels.mts`, not a new
  generation algorithm.
- `progression.isUnlocked`'s rule extends from "previous level id beaten" to "previous
  **required** node beaten" — a branch's two spurs are each independently completable and
  either one's completion unlocks the rejoin node (so a branch is a genuine player choice, not
  a forced detour that blocks progress if the player picks the harder spur first).
- The map itself is drawn on the **same layered-canvas machinery** as the board (§2), reusing
  `lattice-canvas`-style static painting (path nodes + connecting lines precomputed once per
  chapter, repainted only on unlock-state change) — a pulsing glow on the current unlocked
  frontier node is the one animated element, budget-identical to a single small `Tween` in the
  §1.2 tween list rather than a new animation subsystem.

### 4.2 Star ratings

Unchanged from the shipped system — `LevelResult.stars: 0|1|2|3` via `levels.mts::rateLevel`,
recorded max-wise by `progression.applyResult`. No new design needed here; this section exists
to confirm the map's star display (per-node star pips) reads directly from
`PlayerMeta.stars[levelId]`, no new field.

### 4.3 Soft attempt system ("sparks") — proposed extension, not implemented this pass

**The problem, precisely.** The teardown's §2 table calls lives/energy "load-bearing for
retention, but genuinely controversial... the single most-cited 'predatory friction' mechanic
in the genre," and recommends "a soft version... that never blocks free play entirely." The
shipped system (`economy.mts`'s `spendLife`, `scene.mts`'s `handleStart`) is a **hard** gate:
starting *any* level at 0 lives is refused outright, and the only recovery is the 30-minute
regen or the `life-refill` SKU (a payments-touching purchase). That is the exact pattern the
teardown flags.

**The fix, scoped to stay out of "payments changes."** Sparks are a second, orthogonal,
non-monetary resource — never sold, never a `Sku.grant` variant, no new `SKUS` entry — that
soften only the single worst moment: failing a level and wanting to try it *again, right now*.
They do not touch the existing lives system, which stays as-is this pass.

```ts
// Proposed addition to PlayerMeta (types.mts) — NOT implemented this pass.
interface PlayerMeta {
  // ...existing fields unchanged...
  /** Per-level soft-retry credits. Absent key == full (SPARK_CAP). Scoped to one levelId —
   *  losing level 12 never affects level 13's sparks. */
  sparks: Record<number /* levelId */, { n: number; nextAt: number }>;
}
```

Rules:

1. **Cap 3, regen 1 per 20 minutes** (per level id) — full recovery from empty in exactly one
   hour, which is the literal "within an hour" window this section's brief specifies.
2. **On a level loss** (`LevelResult.won === false`), if `sparks[id].n > 0`: the very next
   `{kind:'start', levelId: id}` for that same level **does not spend a life** — it spends one
   spark instead (`sparks[id].n -= 1`). If `sparks[id].n === 0`: the retry proceeds exactly as
   today (spends a life, or is refused at 0 lives) — **no new restriction is ever added**,
   sparks are strictly a bonus path, never a gate. This is what makes the system honestly
   "never hard-blocks": there is no state in which having sparks makes a retry harder than it
   is today, only states in which it's easier.
3. Sparks are consumed **only** by a same-level retry immediately following a loss on that
   level — starting a *different* level, or retrying after a *win*, never touches the spark
   pool. This keeps the mechanic legible as "a free shot right after a near-miss," which is
   precisely the near-miss psychology the teardown's §1 cites (Raviosoft's move-budget tuning,
   the psychologyofgames.com near-miss-effect source) rather than a general life-replacement.
4. Implementation surface for the next pass: one new `economy.mts` function
   (`tickSparks(meta, levelId, now): PlayerMeta`, mirroring `tickLives`'s shape exactly) and one
   `scene.mts::handleStart` branch checking `sparks[id].n` before falling through to today's
   `spendLife` path. No `server.mts` route changes — sparks ride the existing `{kind:'start'}`
   input.

### 4.4 Earnable boosters

No new booster kinds and no new SKUs. The saga map's contribution is a **trigger**, not a new
grant shape: completing a branch-rejoin node (§4.1) for the first time grants one random
booster from the existing `BoosterKind` union (`hammer`/`shuffle`/`extraMoves`/`prismStart`),
reusing the exact `{kind:'booster', booster, amount:1}` shape `Sku.grant` already defines in
`types.mts` — `progression.applyResult` gains one new call site for that grant (first-clear-of-
a-rejoin-node check against `PlayerMeta.stars`/an existing-cleared set), not a new economy
primitive. This keeps the whole saga-map feature payments-free by construction: every reward
path it adds reuses a grant shape the purchase path already uses, just triggered by play instead
of spend.

## 5. Branding — TileSlots, display-only

Per the brief: **display name changes everywhere user-facing; nothing else does.** This keeps
the revert cost at "delete one CSS block and one string constant" if the name changes again.

**What changes** (all inside `src/client.mts`'s `CLIENT_HTML`, nothing server-side):

- The document `<title>` tag.
- One new top-level constant, `var DISPLAY_NAME = "TileSlots";`, referenced everywhere the UI
  currently would otherwise hardcode or infer a game name (header wordmark, win/loss sheet
  copy, any "onestone" string in player-facing text — a search for literal `"onestone"` inside
  `CLIENT_HTML`'s HTML/text nodes, not its `<script>` logic, is the actual change list).
- A CSS-only logo/title treatment: a `.wordmark` class on the header title element using the
  existing `--gold`/glass-panel design tokens already defined in `client.mts`'s `:root` (no new
  color system), so the rebrand is a font-weight/letter-spacing/gradient-text treatment on the
  existing header, not a new visual language.

**What does not change:**

- `package.json`'s `name` field (`@red-cup-engineering/onestone-561-group`) and its
  `exports` map keys.
- The `onestone-service` directory name and every path under it (this document's own path
  included).
- `src/*.mts` module names, the `hashSeed`/`makeRng`/every exported symbol name, route paths in
  `server.mts` (`/session`, `/stream`, `/input`, `/skus`, `/pay`, `/audit`, `/healthz`), env var
  names (`ONESTONE_PORT`, `ONESTONE_SAVE`, `ONESTONE_LEDGER`), and the `onestone.561.group`
  domain framing in `README.md`/`DESIGN.md`'s prose.
- Any persisted save-file shape, ledger account naming, or SKU ids — a player's save/purchase
  history must survive a display-name change untouched.

Rationale for the split: "TileSlots" is a storefront/marketing name; "onestone" is the
engineering identity (the repo's own math-doctrine section explicitly ties the name to the
aperiodic monotile framing) and the payments/audit trail's identity, and those should not be
coupled to a name a marketing decision might change again.
